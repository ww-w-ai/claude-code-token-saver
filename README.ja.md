## 🛡️ 機能 1: Token Guardian

**cache期限切れを検知し、高額な再送信を自動ブロック。**

Claude Codeのプロンプトcache TTLは1時間。1時間以上離席するとcacheが切れる。次のメッセージでcontext全体がフル価格で再送信される。900K tokenなら一発$9。

Token Guardianは最後のレスポンスからの経過時間を追跡する。3,590秒（TTLから10秒のバッファを引いた値）を超えると、プロンプトをブロックして警告を表示する。

```
🚨 キャッシュ期限切れ (68分23秒経過)

プロンプトキャッシュが切れました。このまま実行すると全コンテキストを再送信します。
コストが大幅に増加する可能性があります。

👉 /context — 現在のコンテキスト使用量を確認してから判断
👉 /clear → /continue — リセット後、以前のコンテキストを復元（推奨、最安）
👉 再送信 — そのまま続行（全再キャッシュコスト発生）
```

警告後に同じプロンプトを再送信すれば通過する。警告はアイドル期間ごとに1回だけ発動するため、繰り返し表示されることはない。警告メッセージはOSのlocaleに基づき23言語で表示される。

**効果：** 高額な再cache費用を自動で防止。手間ゼロ。

## 🧠 機能 2: Smart Session Architecture

**インストールするだけでコスト最適化されたワークパターンが自動適用。**

多くのユーザーはすべてをMain sessionで行っている。ファイル読み込み、コード生成、テスト実行。出力はすべてcontextに蓄積され、メッセージごとに再送信される。sessionが膨張し、コストが雪だるま式に増えていく。

Session Architectはsession開始時に委任戦略を自動で注入する。

|                  | Main Session                      | SubTask                               |
| ---------------- | --------------------------------- | ------------------------------------- |
| 役割             | 設計、判断、レビュー              | 実装、コード生成、複数ファイル操作    |
| cache階層        | 1時間 (ephemeral_1h)              | 5分                                   |
| cache書き込みコスト | ＄10/MTok                       | ＄6.25/MTok                           |
| contextサイズ    | 平均 ~94K                         | 平均 ~33K                             |

SubTaskはMainと比べて**cache書き込みコストが37.5%安い**。contextも大幅に小さい。重い作業をSubTaskに委任するだけで、コストが劇的に下がる。

**効果：** Claudeが自動的にコスト効率の良いパターンで動く。意識する必要なし。

## 🔄 機能 3: /continue — Context復元

**`/compact`の代替。LLM呼び出しゼロ。tokenコストゼロ。**

`/compact`はcontext全体（~1M token）をLLMに送り、3.3%に要約する。cacheが切れていた場合、それだけで全再cacheが発生する。情報の欠落も避けられない。

`/continue`はまったく異なるアプローチを取る。前回のsessionのtranscriptを前処理し、直接読み込む。LLM呼び出しなし。コストなし。元の会話がそのまま復元される。

|                         | /compact                          | /continue                        |
| ----------------------- | --------------------------------- | -------------------------------- |
| 仕組み                  | context全体をLLMに送り要約        | transcriptを前処理して直接読み込み |
| LLM呼び出し             | 必要（通常100K+ token）           | 0                                |
| tokenコスト             | 高い                              | 0                                |
| 情報欠落                | あり（3.3%の要約）                | なし（原文保持）                 |
| 処理速度                | 数十秒                            | 1秒未満（60MB+ファイルでも）     |
| cache切れ時             | 全再cacheコストが上乗せ           | 影響なし                         |
| 複数session復元         | 不可                              | 対応                             |

使い方：`/clear` してから `/continue` を実行。前回のsession一覧が表示されるので、復元したいものを選択する。即座に復帰するなら `/continue last`。

**効果：** 前の作業をコストゼロで再開。情報欠落なし。

## 📈 Usage Dashboard (/usage-view)

**「なぜrate limitに当たったのか？」にようやく答えが出る。**

これまでrate limitに当たっても、ただ腹が立つだけだった。原因を知る方法がなかった。どのsessionがtokenを最も消費したのか。コストが急増したのはいつか。利用パターンに傾向はあるか。すべてが見えなかった。

`/usage-view` がすべてを可視化する。インタラクティブなHTMLダッシュボードがブラウザで開き、利用パターンの分析やコスト急増の原因追跡ができる。外部依存なし。単体で動作し、ファイルとして共有も可能。

含まれるもの：

- 日別 / 時間帯別 / 曜日別コスト推移 — tokenが最も消費されるタイミングを特定
- token内訳（入力、出力、cache書き込み、cache読み取り） — コスト要因を把握
- session別コスト分析 — 高コストなタスクを特定
- 5時間ウィンドウタイムライン（Max Planユーザー向け） — rate limitのトリガーを追跡
- AI分析によるインサイト — データを解釈し改善策を提案
- 23言語対応（RTL含む。チャート/テーブルはLTRのまま）

```
/usage-view                  # 全期間、全プロジェクト
/usage-view current          # 現在の5時間ウィンドウのみ
/usage-view last 7 days      # 直近7日間
/usage-view locale ja        # 日本語で表示
```

## ✂️ 機能 5: /setup-git-lite — CCのビルトインGit命令をトリミング

**知らないうちに支払っていた、セッションあたり2,200トークンの隠れコスト。**

### 発見の経緯

2026年4月12日、[GitHubのissue](https://github.com/anthropics/claude-code/issues/47107)により、Claude Codeのビルトイン設定 `includeGitInstructions` が毎セッションで静かにトークンを消費していることが明らかになった。[このgist（spilist）](https://gist.github.com/spilist/b0db92a859192f5ec6199d3f35a81b98)による独自再現で数値が確認された：gitコミット後の毎セッションで **cache書き込みが+6,031トークン**、すべてのAPI呼び出しで **cache読み取りが+1,690トークン**。

### CCソース分析 — トークンの行き先

トークンの発生源をClaude Codeソース（v2.1.88）の2つの独立した注入ポイントに特定した：

**1. `gitStatus` スナップショット（約500トークン）— システムプロンプト**
- `context.ts:36-111` の `getGitStatus()` がブランチ・メインブランチ・ユーザー名・フルステータス（最大2000文字）・**直近5コミット**を収集
- `appendSystemContext`（`utils/api.ts:437`）経由でシステムプロンプトに追記
- 新しいコミット、新しい変更ファイル、ブランチ切り替えのたびにテキストが変わり → プレフィックスcacheが無効化

**2. コミット/PRワークフロー命令（約1,700トークン）— Bashツールの説明**
- `tools/BashTool/prompt.ts:53` が安全プロトコル、コミット手順のステップバイステップ、HEREDOCの例、PRテンプレートを含む60行以上を `Bash` ツールの説明に追記
- システムプロンプトと共にcacheされるが、`tools[]` パラメータとして送信される

### なぜコストが高いのか

cacheの構造（`utils/api.ts:321` の `splitSysPromptPrefix`）はMCPツールの有無により3つのパスをたどる：

- **Path A**（MCP有効 — ほとんどのユーザー）：`gitStatus` が `cacheScope: 'org'` ブロック内に入る。変更があると → 次のセッション開始時にブロック全体が再cacheされ → 6Kトークンの `cache_create` ミスが発生。
- **Path B**（MCPなし）：`gitStatus` が `cacheScope: null` の動的ブロックに入り、毎回のAPI呼び出しで新規 `input_tokens` として送信される — cache漏れはないが、cache節約もない。
- **Path C**（サードパーティプロバイダー / 実験的ベータ無効）：Path Aと同様。

典型的なインタラクティブセッションでは、コミット/PR命令（1.7Kトークン）が `cache_read` 経由で**すべてのAPI呼び出しに**蓄積する。Opus 4.7価格で100回呼び出しのセッションなら、Claudeがトレーニングでほぼカバーしている命令だけで約**$0.08/セッション**になる。

### cc-token-saverの対応方法

`/setup-git-lite` はCCのネイティブパスを無効化し、SessionStartフックで**厳選した280トークンの代替**を注入する。Claudeのデフォルト動作を上書きするもの（安全ルール）は残し、Claudeがトレーニングから既に知っているもの（ステップバイステップのワークフロー、PRテンプレート）は削除した。

**保持 — 11の重要な上書きルール**（Claudeのデフォルトの積極的な動作を慎重さに変えるもの）：
- 明示的なユーザー要求なしにcommit/push/amend/PR/tag/mergeを行わない
- フックのスキップ、main/masterへのforce-push、破壊的操作、git configの変更は行わない
- `.env`、`credentials`、`*.pem`、`secret.*` に一致するファイルはcommitしない
- `git add -A` / `git add .` を避ける
- 複数行コミットメッセージにはHEREDOCを使用し、`Co-Authored-By: Claude` トレーラーを付ける
- インタラクティブフラグ（-i）は使用しない、空のコミットは作らない
- pre-commitフックが失敗した場合 → `--amend` ではなく新しいコミットを作成する

**削除** — ステップバイステップのコミットワークフロー（3ステップ）、ステップバイステップのPRワークフロー（3ステップ）、PRタイトル/本文テンプレート、`gh` コマンドの参照、`-uall` フラグの警告、rebaseでの `--no-edit` 警告、`コミット中にTodoWriteやAgentツールを使用しない` 制約。これらはClaudeがトレーニングのみで正しく構成できるワークフローの冗長な記述だ。

**追加** — コンパクトなgit状態の1行：ブランチ + HEADの短縮sha + サブジェクト + 現在のステータス（変更ファイル最大20件、それ以上は件数）。直近のコミット一覧なし（ClaudeはオンデマンドでGit logを実行できる）。

### 期待される節約効果（Opus 4.7価格、output $25/MTok、input $5/MTok、cache読み取り $0.50/MTok）

| 項目 | 従来 | setup-git-lite適用後 | 節約 |
| ---- | ---- | -------------------- | ---- |
| システムプロンプト読み込み（新規セッションごと） | 約2,200トークン cache_create | 約280トークン cache_create | 約1,920トークン |
| 同一セッション内の繰り返し呼び出し | 約1,700トークン cache_read/call | 約280トークン cache_read/call | 約1,420トークン/call |
| 100回呼び出しセッション（Opus 4.7） | — | — | **約$0.11節約** |
| 1日20セッション × 22営業日 | — | — | **約$48節約/月** |

### 使い方

```bash
/setup-git-lite status     # 読み取り専用の診断 — 現在の状態と変更される内容を確認
/setup-git-lite install    # CCネイティブを無効化し、最小限のフックを有効化
/setup-git-lite revert     # デフォルトに戻す（積極的な処理。下記参照）
/setup-git-lite dismiss-banner    # 推奨ヒントの表示を無効化
/setup-git-lite undismiss-banner  # ヒントの表示を再有効化
/setup-git-lite help       # 全使い方
```

### インストールの動作

`install` は堅牢性のために**2箇所**を変更する：

1. `~/.claude/settings.json` — `"includeGitInstructions": false` を追加
2. シェルプロファイル（`~/.zshrc`、`~/.bashrc` 等）— `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=1` をエクスポートするマーカーブロックを追記

どちらか一方だけでCCネイティブを無効化できるが、環境変数のオーバーライドでネイティブ動作が誤って再有効化されないよう両方を設定する。シェルの変更は新しいシェルからのみ有効になる。

### revertの動作 — 積極的な処理

`revert` は**シェルプロファイルからすべての `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS` エクスポートを削除する**。このスキルのインストール前に手動で追加したものも含む。これは意図的な動作だ — `revert` を実行したということは、クリーンなデフォルトに戻すということを意味する。シェルプロファイルのタイムスタンプ付きバックアップは必ず事前に作成する。

`revert` 実行後も環境変数が必要な場合は、事前にメモしておいて後で再追加すること。

### cc-token-saverをアンインストールする前に

**先に `/setup-git-lite revert` を実行すること**。さもないと `settings.json` に `includeGitInstructions: false` が残ったまま置換フックもない状態になる（Claudeはgitガイダンスをまったく受け取れなくなる）。Claude Codeには現在プラグインのアンインストールライフサイクルフックがないため、自動化はできない。

### トレードオフ

失われるもの（そしてたいていの場合に問題ない理由）：
- Claudeはセッション開始時に事前計算された `git status` / `git log -n 5` を受け取らなくなる。新しいセッションで「何が変わったか？」と聞くと、Claudeが自分でそれらのコマンドを実行する（1回の追加ツール呼び出し、約300トークン）。
- ClaudeはCCの正規3ステップコミット手順を受け取らなくなる。数百のコミットフローにわたるテストで、トレーニングレベルの知識が重要なケース（HEREDOCフォーマット、`--amend` なし、force-pushなし）を処理できることを確認している。明示的なルールとして保持しているためだ。
- PRの本文テンプレート（`## Summary` + `## Test plan`）は注入されない。この形式が必要な場合は、プロジェクトのCLAUDE.mdに記載すること。

### 推奨バナー

CCネイティブのgit命令がまだ有効な場合、cc-token-saverはセッション開始時に**約20%の確率**で1段落のヒントを表示する（`/usage-view` と `/report-limit` の出力にも表示）。`/setup-git-lite dismiss-banner` で永続的に非表示にできる。

## 💡 cacheの仕組み

Claude Codeは毎回のAPI呼び出しで会話履歴全体をモデルに送信する。「API呼び出し」は「ユーザーが入力した1メッセージ」ではない。1つのプロンプトが内部ツール呼び出し -- Grep、Read、Edit、Write -- をトリガーし、それぞれが個別のAPI呼び出しになる。1プロンプトで10回以上のAPI呼び出しが発生することも珍しくない。

プロンプトcacheがこのコストを90%削減する。ただしcacheには寿命がある。

|                     | Main Session                          | SubTask                                |
| ------------------- | ------------------------------------- | -------------------------------------- |
| cache TTL           | 1時間 (ephemeral_1h)                  | 5分                                    |
| cache書き込み       | ＄10/MTok                              | ＄6.25/MTok                             |
| cache読み取り       | ＄0.50/MTok                            | ＄0.50/MTok                             |
| cache切れ時         | context全体がフル価格で再送信         | 影響小（contextが小さいため）          |

cacheが有効でもコストは蓄積する。以下は違いを示すための極端なシナリオ。

### シナリオ：丸一日コーディング（午前3時間 → 昼休み/会議2時間 → 午後3時間）

前提：Opus 4価格、1分に1プロンプト、1プロンプトあたり約5回のAPI呼び出し（約300回/時間）。

#### ❌ cc-token-saverなし

作業のほとんどがMain sessionで行われ、contextが急速に膨張する。

| フェーズ    | 状況                              | contextサイズ              | コスト                                 |
| ----------- | --------------------------------- | -------------------------- | -------------------------------------- |
| 午前3時間   | コーディング（大部分がMainで）    | 100K → 600K (平均 350K)   | 900回 × 350K × ＄0.50/M = ＄157.50     |
| 昼休み/会議 | 2時間離席                         | —                          | —                                      |
| 復帰時      | cache切れ → フル価格で再送信      | 600K フル価格              | 600K × ＄5/M + 600K × ＄10/M = ＄9      |
| 復帰時      | /compact（要約）                  | 600K → LLMに送信          | 600K × ＄0.50/M + 要約出力 = ~＄1.50    |
| 午後3時間   | コーディング継続（contextが再膨張）| 100K → 600K (平均 350K)   | 900回 × 350K × ＄0.50/M = ＄157.50     |
|             | 合計                              |                            | ~＄326                                 |

> この使い方では5時間ウィンドウのrate limitに当たる可能性が高い。**コストも痛いが、本当の問題は作業が完全に止まることだ。Claude Codeが使えなくなる瞬間がここにある。**

#### ✅ cc-token-saverあり

重い作業はSubTaskに委任し、Mainは設計・判断のみに集中。

| フェーズ    | 状況                                         | contextサイズ               | コスト                             |
| ----------- | -------------------------------------------- | --------------------------- | ---------------------------------- |
| 午前3時間   | コーディング（Main：設計、SubTask：実装）     | Main 100K → 300K (平均 200K) | 900回 × 200K × ＄0.50/M = ＄90    |
| 昼休み/会議 | 2時間離席                                    | —                           | —                                  |
| 復帰時      | ⚡ Token Guardianがブロック → /clear + /continue | —                        | ＄0（LLM呼び出しなし）            |
| 午後3時間   | コーディング継続                              | Main 100K → 300K (平均 200K) | 900回 × 200K × ＄0.50/M = ＄90    |
|             | 合計                                         |                             | ~＄180                              |

#### 💰 結果

> **＄326 → ＄180。1日あたり＄146の節約（45%）。**
>
> コスト削減だけではない。同じ時間でtokenの消費が減れば、**rate limitに当たらず作業を続けられる**。これこそが本当の違いだ。

### cc-token-saverが介入するポイント

```
[Session開始]
    │
    ├─ Session Architect → SubTask委任パターンを自動注入
    │                       Mainのcontextを250K以下に維持
    │
[作業中]
    │
    ├─ Status Line → コスト/context/rate limitをリアルタイム監視
    │                  警告ゾーンに入ると即座にアラート
    │
[1時間以上離席]
    │
    ├─ Token Guardian → cache期限切れを検知、再送信前にブロック
    │
[Session再開]
    │
    └─ /continue → 前のcontextをコストゼロで復元（LLM呼び出しなし）
```

## 🔧 ソースインストール & カスタマイズ

```bash
git clone https://github.com/ww-w-ai/cc-token-saver.git
claude plugin marketplace add /path/to/cc-token-saver
claude plugin install cc-token-saver@cc-token-saver
```

cc-token-saverは完全オープンソース。標準プラグイン構造に従ったJavaScript + Bashスクリプトで構成されており、自由にカスタマイズできる。

- **hooks/** — cache期限切れの閾値変更、警告メッセージのカスタマイズ、session architecture ルールの変更
- **scripts/** — 分析ロジック、レポートビルダー、ステータスラインのフォーマット
- **skills/** — /continueや/usage-viewの動作、プロンプトテンプレート
- **locales/** — 翻訳の追加・編集、新しい言語の追加
- **skills/usage-view/** — ダッシュボードのUI/UXデザイン変更

自分好みにカスタマイズしよう。フォークして、試して、もっと良い方法を見つけたらぜひPRを送ってほしい。

## 💡 Tips

### cacheを理解すればコストの行き先が見える

- **1プロンプト ≠ 1 API呼び出し。** ClaudeがGrep、Read、Editを呼ぶたびにcontext全体が再送信される。1プロンプトで10回以上のAPI呼び出しが発生することも珍しくない。明確なプロンプトを書いて不要なツール呼び出しを減らし、コストを削減しよう。
- **cacheの起点は最後のAPI呼び出しであり、最後のプロンプトではない。** 作業を続けていればcacheは切れない。危険なのは離席することだ。Token Guardianが1回だけ自動でブロックしてくれるので、戻ったときにcontextをリセットするか続行するかを選べる。
- **contextサイズ = コスト倍率。** 同じAPI呼び出しでも200Kと800Kではコストが4倍違う。ステータスラインの[CTX]が35%（🟡）を超えたら、SubTaskへの委任を増やすサイン。

### コストを減らす習慣

- **CLAUDE.mdは最小限にする。** 毎回のAPI呼び出しでシステムプロンプトに読み込まれるため、1行ごとにコストがかかる。
- **重い作業はSubTaskに委任する。** コード生成、複数ファイルの編集、テスト実行はMainでやるべきではない。SubTaskはcontextが小さく、cache階層のコストも安い。
- **1時間以上離席する場合は？** `/clear` → 戻ったら `/continue`。contextが$0で復元される。
- **[5H]が70%以上（🟡）になったら？** ペースを落とそう。軽めのレビュータスクに切り替えるか、SubTask委任を増やしてMainのAPI呼び出し回数を減らす。
- **脱線した質問には `/btw` を使う。** 会話履歴に入らないため、contextが膨張しない。
