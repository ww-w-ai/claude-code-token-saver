# 캐시 비용 가이드 — 왜 대부분의 비용이 캐시인가?

AI 코딩 도구 사용 비용의 대부분이 캐시(생성 + 읽기)에 집중되는 것은 정상입니다. 이 문서는 왜 그런지, 그리고 어떻게 관리할 수 있는지를 설명합니다.

## 비밀: LLM 에게 매번 전체 대화를 다시 보내야 한다

LLM은 **상태를 기억하지 않습니다 (stateless)**. 사람과 달리, AI 모델은 이전 대화를 "기억"하는 것이 아니라 매 요청마다 전체 대화 기록을 입력으로 받아서 처음부터 다시 읽습니다.

채팅처럼 보이지만, 실제 API 호출은 이렇게 동작합니다:

```
[ 1번째 요청 ]
→ 시스템 프롬프트 + "버그 수정해줘"
← AI 응답

[ 2번째 요청 ]
→ 시스템 프롬프트 + "버그 수정해줘" + AI 응답 + "테스트도 추가해"
← AI 응답

[ 3번째 요청 ]
→ 시스템 프롬프트 + "버그 수정해줘" + AI 응답 + "테스트도 추가해" + AI 응답 + "커밋해줘"
← AI 응답
```

매 요청마다 이전 내용이 **전부** 포함됩니다. 예를 들어, 50번째 요청에는 1~49번의 모든 대화와 AI 응답까지 입력으로 들어갑니다. 대화가 길어질수록 입력 토큰이 급격히 늘어나는 이유입니다.

여기에 AI 코딩 도구는 시스템 프롬프트(built-in 지시, 설정 파일, 플러그인, MCP 도구 정의 등)도 매번 함께 보내므로, 한마디만 해도 수만 토큰이 입력으로 전송됩니다.

## 캐시란?

이 반복 전송 비용을 줄이기 위해 **프롬프트 캐싱**을 사용합니다. 이전 요청과 동일한 부분을 서버에 저장해두고, 다음 요청 때 "이미 저장된 내용을 활용하여 저렴하게 처리하겠다"는 방식입니다.

- **캐시 생성 (Cache Write)**: 대화 내용을 서버에 저장하는 비용. 첫 요청이나 캐시가 만료된 후 발생.
- **캐시 읽기 (Cache Read)**: 이미 저장된 대화를 재사용하는 비용. 입력 대비 **90% 할인**된 가격이 적용됩니다.

AI 코딩 도구는 대화와 컨텍스트가 길어질 수밖에 없고, 최대 100만 토큰에 달하는 내용을 매 요청마다 새 입력으로 처리해야 합니다. 새로운 질문은 짧더라도 이전 대화 전체가 함께 과금되므로, 대화가 이어질수록 비용이 급격히 누적됩니다.

이 부담을 줄이기 위해 주요 AI 제공자들은 캐시 읽기에 90% 할인을 적용하여, 이미 처리한 내용의 반복 전송 비용을 크게 낮춰줍니다.

## 왜 캐시 비용이 대부분의 비용을 차지하는가?

| 구분            | 호출당 토큰 수    | 비고                   |
| ------------- | ----------- | -------------------- |
| 사용자 입력 (새 토큰) | 수십~수백       | 사용자가 직접 입력하는 대화      |
| AI 출력         | 수백~수천       | AI의 응답               |
| **캐시 읽기**     | **10만~수십만** | 매 호출마다 누적된 전체 대화가 과금 |

매 호출마다 발생하는 캐시 읽기의 양이 입력의 **수천 배**, 90% 할인을 받더라도 비용 기준으로 **수백 배**에 달합니다.

그리고 이 호출은 사용자의 대화만이 아닙니다:

| 호출 주체         | 빈도                 | 매 호출마다 발생하는 캐시 읽기 |
| ------------- | ------------------ | ----------------- |
| 사용자 대화        | 사용자가 메시지를 보낼 때     | 누적된 전체 대화         |
| **AI의 자체 판단** | **사용자 대화보다 훨씬 많음** | 누적된 전체 대화         |

눈에 보이지 않지만 AI는 사용자의 한 마디에 여러 번의 판단을 연쇄적으로 수행합니다 — 어떤 도구를 쓸지 결정하고, 도구 실행 결과를 받아 해석하고, 다음 행동을 결정하는 과정 각각이 전체 컨텍스트를 포함한 LLM 호출입니다. 파일 읽기나 검색 같은 도구 실행 자체는 로컬에서 처리되지만, 그 전후의 판단마다 캐시 읽기 비용이 발생합니다.

### 왜 캐시 생성 비용도 예상보다 큰가?

Anthropic 기준, 캐시 생성 비용은 입력의 1.25배(5분 tier) 또는 2배(1시간 tier)입니다. 이 배율만 보면 입력+출력 비용의 2배를 넘기 어려울 것 같지만, 실제 대시보드를 보면 캐시 생성이 훨씬 큰 비중을 차지합니다.

이유는 두 가지입니다:

| 원인              | 설명                                                                     |
| --------------- | ---------------------------------------------------------------------- |
| **시스템 프롬프트**    | 사용자가 아무것도 입력하지 않아도 기본 수만 토큰 (플러그인/MCP 포함). 이 전체가 캐시 생성 대상              |
| **캐시 만료 후 재생성** | TTL(5분/1시간)이 지난 후 다시 실행하면, 누적된 전체 대화를 처음부터 다시 캐시 생성. 대화가 길수록 재생성 비용 증가 |

즉, 캐시 생성은 "사용자가 입력한 새 토큰"에 대해서만 발생하는 것이 아닙니다. 세션 시작 시 시스템 프롬프트 전체, 캐시 만료 후에는 누적된 대화 전체가 캐시 생성 대상이 됩니다. 10만 토큰짜리 대화에서 캐시가 만료되면, 다음 한 마디에 10만 토큰의 캐시 생성 비용이 한꺼번에 발생하는 것입니다.

**super-token-saver 플러그인이 1시간 자리를 비운 뒤 캐시 만료 경고를 표시하는 이유**가 바로 이것입니다. 경고가 뜨면 현재 컨텍스트 크기를 보고 판단하세요:

- **컨텍스트가 작은 경우**: 컨텍스트가 작으면 캐시 재생성 비용이 크지 않습니다. 같은 프롬프트를 한번 더 입력하면 실행이 되니 그대로 이어가면 됩니다.
- **컨텍스트가 큰 경우**: 컨텍스트가 크면 캐시 비용이 많이 발생합니다. `/clear` 후 `/s-continue last`로 새 세션에서 이어가는 것을 추천합니다. continue 스킬을 통해 이전 대화의 맥락이 자동으로 복원되므로 흐름이 끊기지 않습니다.

## 대응: 캐시 비용을 줄이는 방법

super-token-saver 플러그인은 이 모든 대응을 자동화하거나 쉽게 실행할 수 있도록 설계되었습니다.

### 1. 컨텍스트를 작게 유지 — `/clear` + `/s-continue` ⭐

**비용을 줄이는 가장 핵심적인 방법입니다.** 캐시 비용이 높다는 것은 90% 할인을 받고 있다는 뜻이므로 그 자체는 정상입니다. 하지만 불필요하게 컨텍스트가 커진 상태가 유지되면, 할인을 받더라도 매 호출마다 과금되는 절대 금액이 커집니다. **컨텍스트를 적당한 크기 이내로 유지하는 것이 비용 관리의 핵심**입니다.

주제가 바뀌거나 대화가 길어졌다면 `/clear`로 초기화하고, `/s-continue last`로 이전 맥락을 복원하세요. `/s-continue`는 LLM 호출 없이 이전 대화를 복원하므로 추가 비용이 0입니다.

`/compact`는 대화를 요약하여 컨텍스트를 줄이지만, 요약 과정에서 LLM 호출 비용이 발생하고 대화의 맥락도 손실되므로 추천하지 않습니다.

### 2. 캐시 만료 방지 — Token Guardian (자동)

Anthropic의 메인 세션 캐시는 **1시간 tier**로 유지됩니다. 만료 후 첫 요청에서 전체 대화를 다시 캐시 생성(Write)해야 하므로 큰 비용이 발생합니다.

super-token-saver는 1시간 유휴 상태를 감지하면 **자동으로 경고를 표시**합니다. 경고가 뜨면 위의 1번 방법(`/clear` + `/s-continue`)으로 새 세션에서 이어가는 것이 경제적입니다.

### 3. 무거운 작업은 서브태스크로 위임

코드 생성, 다중 파일 수정 같은 무거운 작업은 메인 세션에서 직접 실행하지 않고 서브태스크(SubTask)로 위임하면 캐시 비용을 줄일 수 있습니다. 서브태스크는 5분 tier 캐시를 사용하여 **캐시 생성 비용이 37.5% 저렴**하고, 독립된 작은 컨텍스트에서 실행되므로 매 호출당 캐시 읽기 양도 적습니다.

super-token-saver는 세션 시작 시 이 작업 분리 패턴을 자동으로 안내합니다.

### 4. 실시간 비용 모니터링 — `/setup-statusline`

`/setup-statusline`을 설치하면 CLI 하단에 실시간 비용/토큰 상태가 표시됩니다: `[RUN] \$0.10/\$12.23 | [5H] 9% | [CTX] 22%`. 호출당 비용이 비정상적으로 높거나 컨텍스트가 커지고 있을 때 즉시 알 수 있어, 비용이 급증하기 전에 대응할 수 있습니다.

### 5. 비용 패턴 분석 — `/usage-view`

`/usage-view`로 전체 사용 내역을 대시보드로 확인하세요. 일별/시간대별 비용 추이, 세션별 토큰 구성, 캐시 효율성 등을 시각적으로 파악할 수 있습니다. 어떤 작업에서 비용이 급증했는지, 어떤 패턴이 비효율적인지 한눈에 보입니다.

### 6. 시스템 프롬프트 최적화

시스템 프롬프트에 로드되는 플러그인, MCP 서버, 스킬이 많을수록 초기 캐시 생성 비용이 높아집니다. 사용하지 않는 것은 제거하세요.

super-token-saver의 `/setup-git-lite`는 Claude Code 기본 Git 지시문(~2,200 토큰)을 핵심 280 토큰으로 축소합니다. 이를 통해 매 세션 Git 지시문 관련 시스템 프롬프트를 약 88% 줄입니다.

### 7. 도구 선택 — 컨텍스트에 들어가는 양이 다르다

한 번 읽은 파일 내용은 컨텍스트에 남아서 이후 모든 호출의 캐시 읽기에 계속 누적됩니다. 파일 하나를 통째로 읽으면 수천~수만 토큰이 컨텍스트에 추가되고, 이후 모든 호출에서 그 양만큼 캐시 읽기 비용이 계속 발생합니다.

특히 코딩 작업은 여러 파일을 동시에 다루는 경우가 많아서, 파일 3~4개만 전체로 읽어도 컨텍스트가 급격히 커질 수 있습니다. 어떤 도구로 코드를 탐색하느냐에 따라 컨텍스트 증가량이 크게 달라지므로, 적절한 도구 선택이 중요합니다.

| 도구                      | 용도               | 컨텍스트 영향                 | 언제 사용                                    |
| ----------------------- | ---------------- | ----------------------- | ---------------------------------------- |
| **Grep**                | 패턴으로 코드 검색       | **최소** — 매칭된 라인만 반환     | 특정 함수명, 변수, 문자열을 찾을 때                    |
| **Glob**                | 파일명 패턴 검색        | **최소** — 파일 경로만 반환      | `*.ts`, `src/**/*.test.js` 등 파일 위치를 찾을 때 |
| **LSP**                 | 심볼 정의, 참조, 타입 조회 | **최소** — 정의/시그니처만 반환    | 함수 정의로 이동, 참조 찾기, 타입 확인                  |
| **Read** (offset/limit) | 파일의 특정 부분 읽기     | **중간** — 지정한 범위만 반환     | 특정 라인 범위의 코드를 봐야 할 때                     |
| **Read** (전체)           | 파일 전체 읽기         | **큼** — 파일 전체가 컨텍스트에 추가 | 파일 구조를 전체적으로 파악해야 할 때만                   |

"이 파일 전체를 읽어봐"보다 "이 함수를 찾아봐"가 컨텍스트를 수십~수백 배 적게 사용합니다.

수정과 비교에도 같은 원리가 적용됩니다:

| 도구                  | 용도               | 컨텍스트 영향                     |
| ------------------- | ---------------- | --------------------------- |
| **Edit**            | 기존 파일 수정         | **최소** — 변경된 diff만 컨텍스트에 추가 |
| **Write**           | 새 파일 생성 / 전체 재작성 | **큼** — 파일 전체가 컨텍스트에 추가     |
| **git diff / diff** | 파일·폴더 비교         | **최소** — 차이점만 반환            |
| 두 파일을 각각 Read       | 파일·폴더 비교         | **큼** — 양쪽 파일 전체가 컨텍스트에 추가  |

super-token-saver는 세션 시작 시 AI에게 이 도구 선택 가이드를 자동으로 주입하여, 가능한 한 가벼운 도구를 먼저 사용하도록 유도합니다.

### API 직접 호출 시 추가 캐시 제어 옵션

위 비교는 AI 코딩 도구(Claude Code, Codex, Gemini CLI) 사용자 기준입니다. API를 직접 호출하는 개발자는 캐시를 더 세밀하게 제어할 수 있습니다.

**Anthropic**

- `cache_control`: breakpoint를 지정하여 캐시 끝 지점을 명시적으로 설정 가능. 미지정 시 자동 결정
- TTL tier(5분/1시간)를 요청 시 선택 가능

**OpenAI**

- `prompt_cache_key`: 동일한 키를 가진 요청을 같은 서버로 라우팅하여 캐시 히트율 향상. Codex는 내부적으로 `conversation_id`를 자동 설정
- `prompt_cache_retention: "24h"`: Extended 캐시 유지. 기본 5~10분 → 최대 24시간으로 연장 (추가 비용 없음, 보장 없음). Codex는 이 옵션을 사용하지 않음

**Google Gemini**

- 명시적 캐싱 (`CachedContent`): TTL을 1분~48시간으로 직접 지정하여 캐시 히트를 보장. 저장 수수료 발생 (\$4.50/MTok/hour, Pro 기준). 캐시 내용 업데이트 시 새 CachedContent를 수동 생성해야 함. Gemini CLI는 이 기능을 사용하지 않음

> **참고**: 위 옵션들은 AI 코딩 도구에서는 노출되지 않으며, 사용자가 직접 제어할 수 없습니다. AI 코딩 도구 사용자는 본문의 "대응: 캐시 비용을 줄이는 방법"을 참고하세요.
