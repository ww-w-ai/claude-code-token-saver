# キャッシュ費用ガイド — コストの大部分がキャッシュである理由

AIコーディングツールのコストの大半がキャッシュ操作（書き込み＋読み取り）に費やされるのは正常です。本ドキュメントでは、その理由と対処法を解説します。

## 秘密：メッセージを送るたびに会話全体が再送信される

LLMは**ステートレス**です。人間と違い、AIモデルは過去の会話を「記憶」していません。リクエストごとに会話履歴全体を入力として受け取ります。

見た目はチャットですが、実際のAPI呼び出しはこう動いています：

```
[ リクエスト 1 ]
→ システムプロンプト + "このバグを直して"
← AIの応答

[ リクエスト 2 ]
→ システムプロンプト + "このバグを直して" + AIの応答 + "テストも追加して"
← AIの応答

[ リクエスト 3 ]
→ システムプロンプト + "このバグを直して" + AIの応答 + "テストも追加して" + AIの応答 + "コミットして"
← AIの応答
```

すべてのリクエストに**過去の全コンテンツ**が含まれます。例えば50回目のリクエストには、それ以前の49回分の会話とAI応答がすべて含まれます。会話が長くなるにつれて入力トークンが急速に増加するのはこのためです。

さらに、AIコーディングツールはシステムプロンプト（組み込み命令、設定ファイル、プラグイン、MCPツール定義など）を毎回送信します。そのため、たった一行のメッセージでも数万トークンの入力が発生します。

## キャッシュとは？

**プロンプトキャッシュ**は、この繰り返し送信のコストを削減します。入力のうち変更されていない部分をサーバーに保存し、後続のリクエストで割引価格で再利用できるようにします。

- **Cache Write**：会話内容をサーバーに保存するコスト。初回リクエスト時またはキャッシュ期限切れ後に発生します。
- **Cache Read**：すでに保存された会話を再利用するコスト。通常入力の**90%割引**で課金されます。

AIコーディングツールは必然的に長い会話と大規模なコンテキストを生み出し、1リクエストあたり最大100万トークンに達します。新しい質問が短くても、過去の会話全体が一緒に課金されるため、会話が長くなるほどコストは急速に蓄積されます。

この負担を軽減するため、主要AIプロバイダーはCache Readに90%の割引を適用し、既に処理済みのコンテンツの再送信コストを大幅に引き下げています。

## なぜキャッシュが総コストの大部分を占めるのか？

| カテゴリ | 1回あたりのトークン数 | 備考 |
|---|---|---|
| ユーザー入力（新規トークン） | 数十〜数百 | ユーザーが実際に入力した内容 |
| AI出力 | 数百〜数千 | AIの応答 |
| **Cache Read** | **10万〜数十万** | 蓄積された会話全体が毎回課金される |

1回の呼び出しにおけるCache Readの量は、入力の**数千倍**です。90%割引があっても、絶対額ではCache Readが依然として支配的です。

そして、これらの呼び出しはユーザーメッセージだけではありません：

| 呼び出し元 | 頻度 | 1回あたりのCache Read |
|---|---|---|
| ユーザーメッセージ | ユーザーがメッセージを送信した時 | 蓄積された会話全体 |
| **AIの自律的な判断** | **ユーザーメッセージ1回につき複数回** | 蓄積された会話全体 |

ユーザーの1つのメッセージに対して、AIは見えないところで複数の判断を順次実行します。どのツールを使うか、ツールの結果をどう解釈するか、次にどうするか。これらの判断はそれぞれコンテキスト全体を含む完全なLLM呼び出しです。ツール実行自体（ファイル読み取り、検索）はローカルで行われますが、ツール使用前後の判断にはCache Readコストが発生します。

### なぜCache Writeコストも予想以上に大きいのか？

Anthropicの場合、Cache Writeコストは入力の1.25倍（5分tier）または2倍（1時間tier）です。この倍率だけ見ると、Cache Writeが入力＋出力コストの2倍を超えることはなさそうですが、実際にはCache Writeがはるかに大きな割合を占めます。

理由は2つあります：

| 原因 | 説明 |
|---|---|
| **システムプロンプト** | ユーザーが何も入力する前に、数万トークンが存在する（プラグイン/MCP利用時）。これらすべてにCache Writeコストが発生 |
| **期限切れ後の再作成** | TTL（5分 / 1時間）が切れると、蓄積された会話全体を再キャッシュする必要がある。会話が長いほど再作成コストが高くなる |

つまり、Cache Writeは「ユーザーが入力した新しいトークン」に対してだけ発生するのではありません。セッション開始時にシステムプロンプト全体がキャッシュされ、期限切れ後は蓄積された会話全体がCache Writeの対象になります。10万トークンの会話のキャッシュが切れると、1回のメッセージで10万トークン分のCache Writeが一度に発生します。

**super-token-saverプラグインが1時間の無操作後にキャッシュ期限切れ警告を表示するのは、まさにこのためです。** 警告が表示されたら、現在のコンテキストサイズを確認してください：

- **コンテキストが小さい場合**：キャッシュ再作成コストは許容範囲内です。そのまま作業を続けてください。コストは低く済みます。
- **コンテキストが大きい場合**：キャッシュコストが大きくなります。`/clear` 後に `/s-continue last` で新しいセッションで再開することをお勧めします。continueスキルが前の会話コンテキストを自動復元するので、作業の流れは中断されません。

## キャッシュコストを削減する戦略

super-token-saverプラグインは、これらの戦略をすべて自動化または簡素化するよう設計されています。

### 1. コンテキストを小さく保つ — `/clear` + `/s-continue` ⭐

**これがコスト削減の最も重要な方法です。** キャッシュコストが高いということは90%割引が適用されているということで、それ自体は正常です。しかし、コンテキストが不必要に大きくなったまま放置すると、割引があっても1回あたりの絶対コストが増加します。**コンテキストサイズの管理が最も効果的なコスト管理戦略です。**

トピックが変わったり会話が長くなったら、`/clear` でリセットし、`/s-continue last` で前のコンテキストを復元します。`/s-continue` はLLM呼び出しなしで前の会話を復元するため、コストはゼロです。

`/compact` は会話を要約してコンテキストを縮小しますが、要約プロセス自体にLLM呼び出しコストが発生し、会話の詳細が失われます。推奨しません。

### 2. キャッシュ期限切れを防ぐ — Token Guardian（自動）

Anthropicのメインセッションキャッシュは**1時間tier**を使用します。期限切れ後、最初のリクエストで会話全体をCache Writeとして再作成する必要があり、コストが高くなります。

super-token-saverは1時間のアイドル状態を検知し、**自動的に警告を表示します**。警告が表示されたら、上記の方法1（`/clear` + `/s-continue`）で新しいセッションで続けるのが最も経済的です。

### 3. 重い作業をSubTasksに委任する

コード生成や複数ファイルの編集などの重い作業は、メインセッションで直接行う代わりにSubTasksに委任できます。SubTasksは5分cache tierを使用するため**Cache Writeが37.5%安くなり**、独立した小さなコンテキストで実行されるため、1回あたりのCache Read量も削減されます。

super-token-saverはセッション開始時に、この作業分離パターンを自動的にガイドします。

### 4. リアルタイムコスト監視 — `/setup-statusline`

`/setup-statusline` をインストールすると、CLIの下部にリアルタイムのコスト/トークン状況が表示されます：`[RUN] \$0.10/\$12.23 | [5H] 9% | [CTX] 22%`。1回あたりの異常に高いコストやコンテキストの増大をすぐに発見でき、コストが急増する前に対処できます。

### 5. コストパターン分析 — `/usage-view`

`/usage-view` で使用履歴全体をダッシュボードとして確認できます。日別/時間別のコスト推移、セッションごとのトークン構成、キャッシュ効率を可視化します。どのタスクがコスト急増を引き起こし、どのパターンが非効率かを一目で把握できます。

### 6. システムプロンプトの最適化

システムプロンプトに読み込まれるプラグイン、MCPサーバー、スキルが多いほど、初回のCache Writeコストが高くなります。使用していないものは削除してください。

super-token-saverの `/setup-git-lite` は、Claude Codeのデフォルトのgit命令（約2,200トークン）をコア280トークンに縮小します。セッションごとのGit関連システムプロンプトを約88%削減します。

### 7. ツール選択 — ツールによってコンテキストへの影響が異なる

一度読み込まれたファイルの内容はコンテキストに残り、以降のすべての呼び出しでCache Readとして蓄積されます。1つのファイルを丸ごと読み込むだけで、コンテキストに数千〜数万トークンが追加され、その量が以降のすべての呼び出しで課金されます。

コーディング作業では複数のファイルを同時に扱うことが多く、3〜4ファイルを丸ごと読み込むだけでコンテキストが劇的に増大します。適切なツールを選ぶことで、コンテキストの増大に大きな差が生まれます。

| ツール | 用途 | コンテキストへの影響 | 使用場面 |
|---|---|---|---|
| **Grep** | パターンでコードを検索 | **最小限** — 一致する行のみ返す | 特定の関数名、変数、文字列の検索 |
| **Glob** | 名前パターンでファイルを検索 | **最小限** — ファイルパスのみ返す | `*.ts`、`src/**/*.test.js` などのファイル検索 |
| **LSP** | シンボル定義、参照、型情報 | **最小限** — 定義/シグネチャのみ返す | 定義へ移動、参照検索、型チェック |
| **Read**（offset/limit） | ファイルの特定部分を読む | **中程度** — 指定範囲のみ返す | 特定の行範囲が必要な場合 |
| **Read**（全体） | ファイル全体を読む | **大きい** — ファイル全体がコンテキストに追加 | ファイル構造全体の理解が必要な場合のみ |

「このファイル全体を読んで」は「この関数を探して」の数十〜数百倍のコンテキストを使用します。

編集や比較にも同じ原則が当てはまります：

| ツール | 用途 | コンテキストへの影響 |
|---|---|---|
| **Edit** | 既存ファイルの修正 | **最小限** — 差分のみコンテキストに追加 |
| **Write** | 新規ファイル作成 / 全面書き換え | **大きい** — ファイル全体がコンテキストに追加 |
| **git diff / diff** | ファイル/フォルダの比較 | **最小限** — 差分のみ返す |
| 両方のファイルを個別にRead | ファイル/フォルダの比較 | **大きい** — 両ファイル全体がコンテキストに追加 |

super-token-saverはセッション開始時にこのツール選択ガイドをAIに自動注入し、軽量なツールの優先使用を促します。

## 付録：AIプロバイダー間のキャッシュ比較

### キャッシュコスト

| プロバイダー | Cache Writeコスト | Cache Read割引 | キャッシュストレージコスト |
|---|---|---|---|
| **Anthropic**<br/>(Claude Code) | 5分tier: 入力の1.25倍<br/>1時間tier: 入力の2倍 | 90%割引 | なし |
| **OpenAI**<br/>(Codex) | 上乗せなし（入力と同額） | 90%割引 | なし |
| **Google Gemini**<br/>(Gemini CLI) | 上乗せなし（入力と同額） | 90%割引 | なし |

> **注**：Cache Readの割引率はモデルによって異なります。ここに示した数値は各プロバイダーの最新フラッグシップモデルのものです。

### キャッシュ有効期間（TTL）

| プロバイダー | TTL | 保証 |
|---|---|---|
| **Anthropic**<br/>(Claude Code) | 5分または1時間 | **明示的に定義** |
| **OpenAI**<br/>(Codex) | 通常、非アクティブ後5〜10分で削除。オフピーク時は最大1時間維持される場合あり | **保証なし** — 公式ドキュメントでは "generally"、"up to" と表記 |
| **Google Gemini**<br/>(Gemini CLI) | 非公開 | **保証なし** — 保証付きTTLの明示的キャッシュはAPI経由で利用可能（有料） |

> **注**：Claude Codeでの実験に基づくと、メインセッションは通常1時間tierを、SubTasksは5分tierを使用します。

### API直接呼び出しによる追加のキャッシュ制御オプション

上記の比較はAIコーディングツールユーザー（Claude Code、Codex、Gemini CLI）の視点です。APIを直接呼び出す開発者には、より細かいキャッシュ制御が可能です。

**Anthropic**

- `cache_control`：キャッシュ境界を明示的に定義するブレークポイントを設定。未指定の場合は自動決定。
- TTL tier（5分 / 1時間）をリクエストごとに選択可能。

**OpenAI**

- `prompt_cache_key`：同じキーのリクエストを同じサーバーにルーティングし、キャッシュヒット率を向上。Codexは内部的に `conversation_id` を自動設定。
- `prompt_cache_retention: "24h"`：キャッシュ保持期間の延長。デフォルトの5〜10分を最大24時間に延長（追加費用なし、保証なし）。Codexはこのオプションを使用しません。

**Google Gemini**

- 明示的キャッシュ（`CachedContent`）：TTLを1分〜48時間に設定してキャッシュヒットを保証。ストレージ料金が発生（Proの場合 \$4.50/MTok/時間）。キャッシュ内容の更新には新しいCachedContentの手動作成が必要。Gemini CLIはこの機能を使用しません。

> **注**：これらのオプションはAIコーディングツールでは公開されておらず、ユーザーが直接制御することはできません。AIコーディングツールのユーザーは、本文の「キャッシュコストを削減する戦略」セクションを参照してください。
