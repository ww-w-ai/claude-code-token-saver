# 缓存成本指南 — 为什么大部分费用来自缓存

AI编程工具的大部分费用来自缓存操作（写入+读取），这是正常现象。本文档将解释原因以及应对方法。

## 秘密：每条消息都会重新发送整个对话

LLM是**无状态的**。与人类不同，AI模型不会"记住"之前的对话——它在每次请求时都会接收完整的对话历史作为输入。

看起来像聊天，但实际的API调用是这样工作的：

```
[ 请求 1 ]
→ 系统提示词 + "修复这个bug"
← AI回复

[ 请求 2 ]
→ 系统提示词 + "修复这个bug" + AI回复 + "也加上测试"
← AI回复

[ 请求 3 ]
→ 系统提示词 + "修复这个bug" + AI回复 + "也加上测试" + AI回复 + "提交一下"
← AI回复
```

每次请求都包含**所有**之前的内容。例如，第50次请求包含了前49次的全部对话和AI回复。这就是为什么对话越长，输入token增长越快。

此外，AI编程工具每次请求都会发送系统提示词（内置指令、配置文件、插件、MCP工具定义等），因此即使只发送一行消息，也会产生数万个输入token。

## 什么是缓存？

**提示词缓存**降低了这种重复传输的成本。它将输入中未改变的部分存储在服务器上，使后续请求可以以折扣价格重复使用。

- **Cache Write**：将对话内容存储到服务器的成本。在首次请求或缓存过期后发生。
- **Cache Read**：重复使用已存储对话的成本。相比标准输入价格享受**90%折扣**。

AI编程工具必然会产生长对话和大上下文，单次请求最多可达100万token。即使你的新问题很短，之前的整个对话都会一并计费，所以对话越长，费用积累越快。

为了减轻这一负担，主流AI服务商对Cache Read提供90%折扣，大幅降低已处理内容的重传成本。

## 为什么缓存在总费用中占比如此之高？

| 类别 | 每次调用的token数 | 说明 |
|---|---|---|
| 用户输入（新token） | 几十到几百 | 用户实际输入的内容 |
| AI输出 | 几百到几千 | AI的回复 |
| **Cache Read** | **10万到几十万** | 累积的整个对话每次调用都会计费 |

每次调用中Cache Read的量是输入的**数千倍**。即使有90%折扣，从绝对金额来看Cache Read仍然占主导地位。

而且这些调用不仅仅来自用户消息：

| 调用方 | 频率 | 每次调用的Cache Read |
|---|---|---|
| 用户消息 | 用户发送消息时 | 累积的整个对话 |
| **AI的自主决策** | **每条用户消息触发多次** | 累积的整个对话 |

对于用户的一条消息，AI会在后台依次执行多个决策——选择使用哪个工具、解读工具结果、决定下一步操作。每个决策都是包含完整上下文的LLM调用。工具执行本身（文件读取、搜索）在本地运行，但工具使用前后的决策过程都会产生Cache Read成本。

### 为什么Cache Write成本也比预期大？

对于Anthropic，Cache Write成本是输入的1.25倍（5分钟tier）或2倍（1小时tier）。按这个倍率来看，Cache Write似乎不应该超过输入+输出成本的2倍——但实际上，Cache Write占了更大的比例。

原因有两个：

| 原因 | 说明 |
|---|---|
| **系统提示词** | 用户还没输入任何内容时就已经有数万token（使用插件/MCP时）。这些全部需要承担Cache Write成本 |
| **过期后重建** | TTL（5分钟 / 1小时）到期后，累积的整个对话需要重新缓存。对话越长，重建成本越高 |

也就是说，Cache Write不仅仅发生在"用户输入的新token"上。会话开始时整个系统提示词会被缓存；过期后，累积的整个对话都会成为Cache Write的对象。如果一个10万token的对话缓存过期了，一条消息就会触发10万token的Cache Write。

**这正是super-token-saver插件在闲置1小时后显示缓存过期警告的原因。** 看到警告时，请检查当前上下文大小：

- **上下文较小**：缓存重建成本在可接受范围内。继续工作即可，费用不高。
- **上下文较大**：缓存成本会很可观。建议执行 `/clear` 然后 `/s-continue last` 在新会话中恢复。continue技能会自动恢复之前的对话上下文，工作流程不会中断。

## 降低缓存成本的策略

super-token-saver插件的设计目标就是自动化或简化以下所有策略。

### 1. 保持上下文精简 — `/clear` + `/s-continue` ⭐

**这是降低成本最重要的方法。** 缓存成本高意味着你享受了90%折扣——这本身是正常的。但如果上下文不必要地增大且长期保持，即使有折扣，每次调用的绝对成本也会上升。**控制上下文大小是最有效的成本管理策略。**

当话题切换或对话变长时，执行 `/clear` 重置，然后用 `/s-continue last` 恢复之前的上下文。`/s-continue` 无需LLM调用即可恢复之前的对话，成本为零。

`/compact` 通过总结对话来缩小上下文，但总结过程本身需要LLM调用且会丢失对话细节。不推荐使用。

### 2. 防止缓存过期 — Token Guardian（自动）

Anthropic的主会话缓存使用**1小时tier**。过期后，首次请求需要将整个对话重新创建为Cache Write，成本很高。

super-token-saver检测到1小时闲置状态后会**自动显示警告**。看到警告时，使用上面的方法1（`/clear` + `/s-continue`）在新会话中继续是最经济的做法。

### 3. 将繁重工作委托给SubTasks

代码生成或多文件编辑等繁重任务可以委托给SubTasks，而不是在主会话中直接执行。SubTasks使用5分钟cache tier，**Cache Write便宜37.5%**，并且在独立的小上下文中运行，减少了每次调用的Cache Read量。

super-token-saver在会话开始时自动引导这种工作分离模式。

### 4. 实时成本监控 — `/setup-statusline`

安装 `/setup-statusline` 后，CLI底部会显示实时的成本/token状态：`[RUN] \$0.10/\$12.23 | [5H] 9% | [CTX] 22%`。你可以立即发现异常高的单次调用成本或不断增长的上下文，在费用飙升之前及时采取行动。

### 5. 成本模式分析 — `/usage-view`

使用 `/usage-view` 以仪表盘形式查看完整的使用历史。可视化每日/每小时成本趋势、每个会话的token构成和缓存效率。一目了然地看出哪些任务导致了成本飙升，哪些模式效率低下。

### 6. 系统提示词优化

加载到系统提示词中的插件、MCP服务器和技能越多，初始Cache Write成本就越高。请移除不使用的部分。

super-token-saver的 `/setup-git-lite` 将Claude Code默认的Git指令（约2,200 token）精简为核心的280 token——每个会话的Git相关系统提示词减少约88%。

### 7. 工具选择 — 不同工具对上下文的影响差异很大

文件内容一旦被读取，就会留在上下文中，在后续所有调用中作为Cache Read累积。仅读取一个完整文件就可能向上下文添加数千到数万个token，而这些token在之后的每次调用中都会计费。

编程任务通常需要同时处理多个文件——仅完整读取3-4个文件就可能导致上下文急剧增长。选择正确的工具对上下文增长有显著影响。

| 工具 | 用途 | 上下文影响 | 使用场景 |
|---|---|---|---|
| **Grep** | 按模式搜索代码 | **极小** — 仅返回匹配行 | 查找特定函数名、变量、字符串 |
| **Glob** | 按名称模式搜索文件 | **极小** — 仅返回文件路径 | 查找 `*.ts`、`src/**/*.test.js` 等文件 |
| **LSP** | 符号定义、引用、类型信息 | **极小** — 仅返回定义/签名 | 跳转到定义、查找引用、检查类型 |
| **Read**（offset/limit） | 读取文件的特定部分 | **中等** — 仅返回指定范围 | 需要特定行范围时 |
| **Read**（完整） | 读取整个文件 | **大** — 整个文件添加到上下文 | 仅当需要了解完整文件结构时 |

"读取整个文件"使用的上下文是"查找这个函数"的数十到数百倍。

编辑和比较同样遵循这个原则：

| 工具 | 用途 | 上下文影响 |
|---|---|---|
| **Edit** | 修改现有文件 | **极小** — 仅差异部分添加到上下文 |
| **Write** | 创建新文件 / 完全重写 | **大** — 整个文件添加到上下文 |
| **git diff / diff** | 比较文件/文件夹 | **极小** — 仅返回差异 |
| 分别Read两个文件 | 比较文件/文件夹 | **大** — 两个完整文件都添加到上下文 |

super-token-saver在会话开始时自动向AI注入此工具选择指南，鼓励优先使用轻量级工具。

## 附录：AI服务商缓存对比

### 缓存成本

| 服务商 | Cache Write成本 | Cache Read折扣 | 缓存存储成本 |
|---|---|---|---|
| **Anthropic**<br/>(Claude Code) | 5分钟tier: 输入的1.25倍<br/>1小时tier: 输入的2倍 | 90%折扣 | 无 |
| **OpenAI**<br/>(Codex) | 无加价（与输入相同） | 90%折扣 | 无 |
| **Google Gemini**<br/>(Gemini CLI) | 无加价（与输入相同） | 90%折扣 | 无 |

> **注**：Cache Read折扣率因模型而异。此处数据反映的是各服务商最新旗舰模型。

### 缓存有效期（TTL）

| 服务商 | TTL | 保证 |
|---|---|---|
| **Anthropic**<br/>(Claude Code) | 5分钟或1小时 | **明确定义** |
| **OpenAI**<br/>(Codex) | 通常在闲置5-10分钟后被清除；低峰期可能保留最长1小时 | **无保证** — 官方文档使用 "generally"、"up to" 等措辞 |
| **Google Gemini**<br/>(Gemini CLI) | 未公开 | **无保证** — 可通过API使用带保证TTL的显式缓存（付费） |

> **注**：根据我们对Claude Code的实验，主会话通常使用1小时tier，SubTasks使用5分钟tier。

### 通过API直接调用的额外缓存控制选项

以上对比是从AI编程工具用户（Claude Code、Codex、Gemini CLI）的角度出发的。直接调用API的开发者可以进行更精细的缓存控制。

**Anthropic**

- `cache_control`：设置断点以明确定义缓存边界。未指定时自动确定。
- 可以按请求选择TTL tier（5分钟 / 1小时）。

**OpenAI**

- `prompt_cache_key`：将具有相同key的请求路由到同一服务器，提高缓存命中率。Codex内部自动将其设置为 `conversation_id`。
- `prompt_cache_retention: "24h"`：延长缓存保留时间。将默认的5-10分钟延长至最多24小时（无额外费用，不保证）。Codex不使用此选项。

**Google Gemini**

- 显式缓存（`CachedContent`）：设置1分钟到48小时的TTL来保证缓存命中。需要支付存储费（Pro为 \$4.50/MTok/小时）。更新缓存内容需要手动创建新的CachedContent。Gemini CLI不使用此功能。

> **注**：这些选项在AI编程工具中未公开，用户无法直接控制。AI编程工具用户请参考正文中的"降低缓存成本的策略"部分。
