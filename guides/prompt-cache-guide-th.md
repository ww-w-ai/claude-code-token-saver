# คู่มือต้นทุน Cache — ทำไมต้นทุนส่วนใหญ่ของคุณจึงมาจาก Cache

เป็นเรื่องปกติที่ต้นทุนส่วนใหญ่ของเครื่องมือ AI coding จะมาจากการดำเนินการ cache (write + read) เอกสารนี้อธิบายว่าทำไม และจะจัดการอย่างไร

## ความลับ: ทุกข้อความส่งบทสนทนาทั้งหมดซ้ำ

LLM เป็น **stateless** ไม่เหมือนมนุษย์ โมเดล AI ไม่ได้ "จำ" บทสนทนาก่อนหน้า — มันรับประวัติบทสนทนาทั้งหมดเป็น input ในทุกคำขอ

ดูเหมือนแชต แต่การเรียก API จริงทำงานแบบนี้:

```
[ คำขอที่ 1 ]
→ System prompt + "แก้บั๊กนี้"
← การตอบกลับ AI

[ คำขอที่ 2 ]
→ System prompt + "แก้บั๊กนี้" + การตอบกลับ AI + "เพิ่มเทสต์ด้วย"
← การตอบกลับ AI

[ คำขอที่ 3 ]
→ System prompt + "แก้บั๊กนี้" + การตอบกลับ AI + "เพิ่มเทสต์ด้วย" + การตอบกลับ AI + "Commit เลย"
← การตอบกลับ AI
```

ทุกคำขอรวม**ทุกอย่าง**ที่ผ่านมา ตัวอย่างเช่น คำขอที่ 50 จะมีบทสนทนาทั้งหมดและการตอบกลับ AI ทั้ง 49 คำขอก่อนหน้า นี่คือเหตุผลที่ token input เพิ่มขึ้นอย่างรวดเร็วเมื่อบทสนทนายาวขึ้น

นอกจากนี้ เครื่องมือ AI coding ส่ง system prompt (คำสั่งในตัว, ไฟล์คอนฟิก, plugin, คำจำกัดความ tool MCP ฯลฯ) ไปกับทุกคำขอ — ดังนั้นแม้ข้อความเพียงบรรทัดเดียวก็ส่งผลให้มี token input นับหมื่น

## Cache คืออะไร?

**Prompt caching** ลดต้นทุนการส่งซ้ำนี้ มันเก็บส่วนที่ไม่เปลี่ยนแปลงของ input ไว้บนเซิร์ฟเวอร์ เพื่อให้คำขอถัดไปสามารถนำมาใช้ซ้ำได้ในราคาส่วนลด

- **Cache Write**: ต้นทุนการจัดเก็บเนื้อหาบทสนทนาบนเซิร์ฟเวอร์ เกิดขึ้นในคำขอแรกหรือหลัง cache หมดอายุ
- **Cache Read**: ต้นทุนการนำเนื้อหาที่จัดเก็บแล้วกลับมาใช้ คิดที่**ส่วนลด 90%** เทียบกับ input มาตรฐาน

เครื่องมือ AI coding สร้างบทสนทนายาวและบริบทขนาดใหญ่โดยธรรมชาติ สูงถึง 1 ล้าน token ต่อคำขอ แม้คำถามใหม่ของคุณจะสั้น แต่บทสนทนาก่อนหน้าทั้งหมดก็ถูกคิดค่าใช้จ่ายร่วมด้วย ทำให้ต้นทุนสะสมอย่างรวดเร็วเมื่อบทสนทนายาวขึ้น

เพื่อลดภาระนี้ ผู้ให้บริการ AI หลักให้ส่วนลด 90% สำหรับ cache read ลดต้นทุนการส่งเนื้อหาที่ประมวลผลแล้วซ้ำได้อย่างมีนัยสำคัญ

## ทำไม Cache จึงครองสัดส่วนต้นทุนรวม?

| หมวดหมู่ | Token ต่อการเรียก | หมายเหตุ |
|---|---|---|
| Input ของผู้ใช้ (token ใหม่) | หลักสิบถึงหลักร้อย | สิ่งที่ผู้ใช้พิมพ์จริง |
| Output AI | หลักร้อยถึงหลักพัน | การตอบกลับของ AI |
| **Cache read** | **100K–หลักแสน K** | บทสนทนาสะสมทั้งหมดถูกคิดค่าใช้จ่ายทุกการเรียก |

ปริมาณ cache read ต่อการเรียก**มากกว่า input หลายพันเท่า** แม้มีส่วนลด 90% cache read ก็ยังครองสัดส่วนในแง่จำนวนเงินดอลลาร์สัมบูรณ์

และการเรียกเหล่านี้ไม่ได้มาจากข้อความของผู้ใช้เท่านั้น:

| ผู้เรียก | ความถี่ | Cache Read ต่อการเรียก |
|---|---|---|
| ข้อความผู้ใช้ | เมื่อผู้ใช้ส่งข้อความ | บทสนทนาสะสมทั้งหมด |
| **การตัดสินใจของ AI เอง** | **หลายการเรียกต่อข้อความผู้ใช้หนึ่งข้อความ** | บทสนทนาสะสมทั้งหมด |

โดยที่มองไม่เห็น AI ทำการตัดสินใจหลายครั้งต่อเนื่องสำหรับข้อความผู้ใช้หนึ่งข้อความ — ตัดสินใจว่าจะใช้ tool ไหน ตีความผลลัพธ์ของ tool ตัดสินใจการกระทำถัดไป การตัดสินใจแต่ละครั้งเป็นการเรียก LLM แบบเต็มที่รวมบริบททั้งหมด การทำงานของ tool เอง (อ่านไฟล์, ค้นหา) ทำงานในเครื่อง แต่การตัดสินใจก่อนและหลังการใช้ tool แต่ละครั้งก่อให้เกิดต้นทุน cache read

### ทำไมต้นทุน Cache Write จึงใหญ่กว่าที่คาดไว้?

สำหรับ Anthropic ต้นทุน cache write คือ 1.25x input (tier 5 นาที) หรือ 2x input (tier 1 ชั่วโมง) ด้วยตัวคูณเหล่านี้ ดูเหมือนว่า cache write ไม่น่าจะเกิน 2x ต้นทุน input+output — แต่ในทางปฏิบัติ cache write กินสัดส่วนที่ใหญ่กว่ามาก

สองเหตุผล:

| สาเหตุ | คำอธิบาย |
|---|---|
| **System prompt** | นับหมื่น token ก่อนที่ผู้ใช้จะพิมพ์อะไร (กับ plugin/MCP) ทั้งหมดนี้ถูกคิดค่า cache write |
| **การสร้างใหม่หลังหมดอายุ** | หลัง TTL (5 นาที / 1 ชั่วโมง) หมดอายุ บทสนทนาสะสมทั้งหมดต้องถูก cache ใหม่ ยิ่งบทสนทนายาว ต้นทุนการสร้างใหม่ยิ่งสูง |

กล่าวคือ cache write ไม่ได้เกิดขึ้นเฉพาะ "token ใหม่ที่ผู้ใช้พิมพ์" เท่านั้น ตอนเริ่มเซสชัน system prompt ทั้งหมดถูก cache; หลังหมดอายุ บทสนทนาสะสมทั้งหมดกลายเป็นเป้าหมาย cache write ถ้า cache ของบทสนทนา 100K token หมดอายุ ข้อความเดียวจะทำให้เกิด cache write 100K token ทั้งหมดในครั้งเดียว

**นี่คือเหตุผลที่ plugin super-token-saver แสดงคำเตือนการหมดอายุ cache หลังไม่ได้ใช้งาน 1 ชั่วโมง** เมื่อคำเตือนปรากฏ ให้ตรวจสอบขนาดบริบทปัจจุบันของคุณ:

- **บริบทเล็ก**: ต้นทุนการสร้าง cache ใหม่ยังพอรับได้ ทำงานต่อไปเลย — ต้นทุนต่ำ
- **บริบทใหญ่**: ต้นทุน cache จะสูงมาก เราแนะนำ `/clear` ตามด้วย `/s-continue last` เพื่อทำงานต่อในเซสชันใหม่ skill continue จะกู้คืนบริบทบทสนทนาก่อนหน้าโดยอัตโนมัติ จึงไม่กระทบขั้นตอนการทำงาน

## กลยุทธ์ลดต้นทุน Cache

Plugin super-token-saver ออกแบบมาเพื่อทำให้กลยุทธ์เหล่านี้ทั้งหมดเป็นอัตโนมัติหรือง่ายขึ้น

### 1. รักษาบริบทให้เล็ก — `/clear` + `/s-continue` ⭐

**นี่คือวิธีที่สำคัญที่สุดในการลดต้นทุน** ต้นทุน cache สูงหมายความว่าคุณได้รับส่วนลด 90% — นั่นเป็นเรื่องปกติ แต่ถ้าบริบทโตขึ้นโดยไม่จำเป็นและยังคงเป็นเช่นนั้น ต้นทุนสัมบูรณ์ต่อการเรียกจะเพิ่มขึ้นแม้มีส่วนลด **การรักษาขนาดบริบทให้อยู่ในการควบคุมเป็นกลยุทธ์จัดการต้นทุนที่มีประสิทธิภาพมากที่สุด**

เมื่อหัวข้อเปลี่ยนหรือบทสนทนายาวขึ้น ให้รัน `/clear` เพื่อรีเซ็ต จากนั้น `/s-continue last` เพื่อกู้คืนบริบทก่อนหน้า `/s-continue` กู้คืนบทสนทนาก่อนหน้าโดยไม่มีการเรียก LLM ใดๆ ดังนั้นต้นทุนเป็นศูนย์

`/compact` ลดบริบทด้วยการสรุปบทสนทนา แต่กระบวนการสรุปเองก่อให้เกิดต้นทุนการเรียก LLM และทำให้สูญเสียรายละเอียดบทสนทนา ไม่แนะนำ

### 2. ป้องกัน Cache หมดอายุ — Token Guardian (อัตโนมัติ)

Cache เซสชันหลักของ Anthropic ใช้ **tier 1 ชั่วโมง** หลังหมดอายุ คำขอแรกต้องสร้างบทสนทนาทั้งหมดเป็น cache write ใหม่ ซึ่งมีต้นทุนสูง

super-token-saver ตรวจจับสถานะ idle 1 ชั่วโมง และ**แสดงคำเตือนโดยอัตโนมัติ** เมื่อคำเตือนปรากฏ การใช้วิธีที่ 1 ข้างต้น (`/clear` + `/s-continue`) เพื่อทำงานต่อในเซสชันใหม่เป็นวิธีที่ประหยัดที่สุด

### 3. มอบหมายงานหนักให้ SubTask

งานหนักเช่น การสร้างโค้ดหรือการแก้ไขหลายไฟล์ สามารถมอบหมายให้ SubTask แทนที่จะรันโดยตรงในเซสชันหลัก SubTask ใช้ tier cache 5 นาที ทำให้ **cache write ถูกลง 37.5%** และทำงานในบริบทที่แยกและเล็กกว่า ลดปริมาณ cache read ต่อการเรียก

super-token-saver แนะนำรูปแบบการแยกงานนี้โดยอัตโนมัติเมื่อเริ่มเซสชัน

### 4. ติดตามต้นทุนแบบเรียลไทม์ — `/setup-statusline`

ติดตั้ง `/setup-statusline` เพื่อแสดงสถานะต้นทุน/token แบบเรียลไทม์ที่ด้านล่างของ CLI: `[RUN] \$0.10/\$12.23 | [5H] 9% | [CTX] 22%` คุณสามารถตรวจพบต้นทุนต่อการเรียกที่สูงผิดปกติหรือบริบทที่โตขึ้นได้ทันที ช่วยให้ดำเนินการก่อนที่ต้นทุนจะพุ่งสูง

### 5. วิเคราะห์รูปแบบต้นทุน — `/usage-view`

ใช้ `/usage-view` เพื่อตรวจสอบประวัติการใช้งานทั้งหมดในรูปแบบ dashboard แสดงภาพแนวโน้มต้นทุนรายวัน/รายชั่วโมง องค์ประกอบ token ต่อเซสชัน และประสิทธิภาพ cache ดูได้ทันทีว่างานไหนทำให้ต้นทุนพุ่ง และรูปแบบไหนไม่มีประสิทธิภาพ

### 6. ปรับปรุง System Prompt

ยิ่งมี plugin, เซิร์ฟเวอร์ MCP, และ skill ที่โหลดเข้า system prompt มากเท่าไหร่ ต้นทุน cache write เริ่มต้นก็ยิ่งสูง ลบสิ่งที่คุณไม่ได้ใช้ออก

`/setup-git-lite` ของ super-token-saver ลดคำสั่ง Git ในตัวของ Claude Code (~2,200 token) เหลือแกนหลัก 280 token — ลดประมาณ 88% ของ system prompt ที่เกี่ยวกับ Git ต่อเซสชัน

### 7. การเลือก Tool — ผลกระทบต่อบริบทแตกต่างกันตาม Tool

เมื่อไฟล์ถูกอ่านแล้ว เนื้อหาจะอยู่ในบริบทและสะสมใน cache read สำหรับทุกการเรียกถัดไป การอ่านไฟล์เดียวทั้งหมดเพิ่ม token หลายพันถึงหลายหมื่นเข้าบริบท และจำนวนนั้นจะถูกคิดค่าใช้จ่ายในทุกการเรียกถัดไป

งาน coding มักเกี่ยวข้องกับหลายไฟล์พร้อมกัน — การอ่านเพียง 3-4 ไฟล์ทั้งหมดก็สามารถทำให้บริบทโตอย่างมาก การเลือก tool ที่ถูกต้องสร้างความแตกต่างอย่างมากในการเติบโตของบริบท

| Tool | วัตถุประสงค์ | ผลกระทบต่อบริบท | ใช้เมื่อไหร่ |
|---|---|---|---|
| **Grep** | ค้นหาโค้ดตามรูปแบบ | **น้อยมาก** — คืนเฉพาะบรรทัดที่ตรงกัน | ค้นหาชื่อฟังก์ชัน ตัวแปร สตริงเฉพาะ |
| **Glob** | ค้นหาไฟล์ตามรูปแบบชื่อ | **น้อยมาก** — คืนเฉพาะ path ไฟล์ | ค้นหาตำแหน่งไฟล์เช่น `*.ts`, `src/**/*.test.js` |
| **LSP** | นิยามสัญลักษณ์ การอ้างอิง ชนิด | **น้อยมาก** — คืนเฉพาะนิยาม/signature | Go to definition, find references, ตรวจสอบชนิด |
| **Read** (offset/limit) | อ่านส่วนเฉพาะของไฟล์ | **ปานกลาง** — คืนเฉพาะช่วงที่ระบุ | เมื่อต้องการช่วงบรรทัดเฉพาะ |
| **Read** (ทั้งหมด) | อ่านทั้งไฟล์ | **มาก** — ไฟล์ทั้งหมดถูกเพิ่มเข้าบริบท | เฉพาะเมื่อต้องเข้าใจโครงสร้างไฟล์ทั้งหมด |

"อ่านไฟล์ทั้งหมดนี้" ใช้บริบทมากกว่า "ค้นหาฟังก์ชันนี้" หลายสิบถึงหลายร้อยเท่า

หลักการเดียวกันใช้กับการแก้ไขและการเปรียบเทียบ:

| Tool | วัตถุประสงค์ | ผลกระทบต่อบริบท |
|---|---|---|
| **Edit** | แก้ไขไฟล์ที่มีอยู่ | **น้อยมาก** — เฉพาะ diff ที่ถูกเพิ่มเข้าบริบท |
| **Write** | สร้างไฟล์ใหม่ / เขียนใหม่ทั้งหมด | **มาก** — ไฟล์ทั้งหมดถูกเพิ่มเข้าบริบท |
| **git diff / diff** | เปรียบเทียบไฟล์/โฟลเดอร์ | **น้อยมาก** — คืนเฉพาะความแตกต่าง |
| อ่านทั้งสองไฟล์แยกกัน | เปรียบเทียบไฟล์/โฟลเดอร์ | **มาก** — ไฟล์เต็มทั้งสองถูกเพิ่มเข้าบริบท |

super-token-saver แทรกคำแนะนำการเลือก tool นี้ให้ AI โดยอัตโนมัติเมื่อเริ่มเซสชัน ส่งเสริมการใช้ tool ที่เบาก่อน

## ภาคผนวก: เปรียบเทียบ Cache ข้ามผู้ให้บริการ AI

### ต้นทุน Cache

| ผู้ให้บริการ | ต้นทุน Cache Write | ส่วนลด Cache Read | ต้นทุนจัดเก็บ Cache |
|---|---|---|---|
| **Anthropic**<br/>(Claude Code) | Tier 5 นาที: 1.25x input<br/>Tier 1 ชั่วโมง: 2x input | ส่วนลด 90% | ไม่มี |
| **OpenAI**<br/>(Codex) | ไม่มีค่าพรีเมียม (เท่ากับ input) | ส่วนลด 90% | ไม่มี |
| **Google Gemini**<br/>(Gemini CLI) | ไม่มีค่าพรีเมียม (เท่ากับ input) | ส่วนลด 90% | ไม่มี |

> **หมายเหตุ**: อัตราส่วนลด cache read แตกต่างกันตามโมเดล ตัวเลขเหล่านี้สะท้อนโมเดล flagship ล่าสุดของแต่ละผู้ให้บริการ

### Cache Time-to-Live (TTL)

| ผู้ให้บริการ | TTL | การรับประกัน |
|---|---|---|
| **Anthropic**<br/>(Claude Code) | 5 นาที หรือ 1 ชั่วโมง | **กำหนดไว้อย่างชัดเจน** |
| **OpenAI**<br/>(Codex) | โดยทั่วไปถูกลบหลังไม่ใช้งาน 5-10 นาที; อาจคงอยู่ถึง 1 ชั่วโมงในช่วงที่ไม่ค่อยมีคนใช้ | **ไม่รับประกัน** — เอกสารอย่างเป็นทางการใช้คำว่า "generally", "up to" |
| **Google Gemini**<br/>(Gemini CLI) | ไม่เปิดเผย | **ไม่รับประกัน** — explicit caching พร้อม TTL รับประกันสามารถใช้ได้ผ่าน API (มีค่าใช้จ่าย) |

> **หมายเหตุ**: จากการทดลองของเรากับ Claude Code เซสชันหลักมักใช้ tier 1 ชั่วโมง ขณะที่ SubTask ใช้ tier 5 นาที

### ตัวเลือกควบคุม Cache เพิ่มเติมผ่านการเรียก API โดยตรง

การเปรียบเทียบข้างต้นมาจากมุมมองของผู้ใช้เครื่องมือ AI coding (Claude Code, Codex, Gemini CLI) นักพัฒนาที่เรียก API โดยตรงมีการควบคุม cache ที่ละเอียดกว่า

**Anthropic**

- `cache_control`: กำหนด breakpoint เพื่อระบุขอบเขต cache อย่างชัดเจน กำหนดอัตโนมัติถ้าไม่ระบุ
- Tier TTL (5 นาที / 1 ชั่วโมง) สามารถเลือกได้ต่อคำขอ

**OpenAI**

- `prompt_cache_key`: ส่งคำขอที่มี key เดียวกันไปยังเซิร์ฟเวอร์เดียวกัน เพิ่มอัตรา cache hit Codex ตั้งค่านี้เป็น `conversation_id` โดยอัตโนมัติภายใน
- `prompt_cache_retention: "24h"`: เก็บ cache นานขึ้น ขยายค่าเริ่มต้น 5-10 นาทีเป็นสูงสุด 24 ชั่วโมง (ไม่มีค่าใช้จ่ายเพิ่ม ไม่รับประกัน) Codex ไม่ใช้ตัวเลือกนี้

**Google Gemini**

- Explicit caching (`CachedContent`): กำหนด TTL ตั้งแต่ 1 นาทีถึง 48 ชั่วโมงเพื่อรับประกัน cache hit มีค่าจัดเก็บ (\$4.50/MTok/ชั่วโมง สำหรับ Pro) การอัปเดตเนื้อหา cache ต้องสร้าง CachedContent ใหม่ด้วยตนเอง Gemini CLI ไม่ใช้ฟีเจอร์นี้

> **หมายเหตุ**: ตัวเลือกเหล่านี้ไม่ได้เปิดให้ใช้ในเครื่องมือ AI coding และผู้ใช้ไม่สามารถควบคุมได้โดยตรง ผู้ใช้เครื่องมือ AI coding ควรดูส่วน "กลยุทธ์ลดต้นทุน Cache" ในเนื้อหาหลัก
