# Cache খরচ গাইড — কেন আপনার বেশিরভাগ খরচ Cache থেকে আসে

AI কোডিং টুলের বেশিরভাগ খরচ cache অপারেশন (লেখা + পড়া) থেকে আসা স্বাভাবিক। এই ডকুমেন্ট ব্যাখ্যা করে কেন, এবং কীভাবে এটি পরিচালনা করবেন।

## রহস্য: প্রতিটি মেসেজ পুরো কথোপকথন আবার পাঠায়

LLM-গুলো **স্টেটলেস**। মানুষের মতো নয়, AI মডেল আগের কথোপকথন "মনে রাখে" না — তারা প্রতিটি রিকোয়েস্টে সম্পূর্ণ কথোপকথনের ইতিহাস ইনপুট হিসেবে পায়।

এটি চ্যাটের মতো দেখায়, কিন্তু আসল API কলগুলো এভাবে কাজ করে:

```
[ রিকোয়েস্ট 1 ]
→ System prompt + "এই বাগটি ঠিক করো"
← AI-এর উত্তর

[ রিকোয়েস্ট 2 ]
→ System prompt + "এই বাগটি ঠিক করো" + AI-এর উত্তর + "টেস্টও যোগ করো"
← AI-এর উত্তর

[ রিকোয়েস্ট 3 ]
→ System prompt + "এই বাগটি ঠিক করো" + AI-এর উত্তর + "টেস্টও যোগ করো" + AI-এর উত্তর + "কমিট করো"
← AI-এর উত্তর
```

প্রতিটি রিকোয়েস্টে **সমস্ত** আগের কন্টেন্ট থাকে। উদাহরণস্বরূপ, ৫০তম রিকোয়েস্টে আগের ৪৯টি রিকোয়েস্টের সম্পূর্ণ কথোপকথন এবং সব AI উত্তর থাকে। এই কারণেই কথোপকথন দীর্ঘ হলে ইনপুট টোকেন দ্রুত বাড়ে।

এর উপরে, AI কোডিং টুলগুলো প্রতিটি রিকোয়েস্টের সাথে system prompt (বিল্ট-ইন নির্দেশনা, কনফিগ ফাইল, প্লাগইন, MCP টুল ডেফিনিশন ইত্যাদি) পাঠায় — তাই এক লাইনের একটি মেসেজও দশ হাজার ইনপুট টোকেন তৈরি করে।

## Caching কী?

**Prompt caching** এই বারবার ট্রান্সমিশনের খরচ কমায়। এটি আপনার ইনপুটের অপরিবর্তিত অংশগুলো সার্ভারে সংরক্ষণ করে যাতে পরবর্তী রিকোয়েস্টগুলো ছাড়ের হারে সেগুলো পুনরায় ব্যবহার করতে পারে।

- **Cache লেখা**: সার্ভারে কথোপকথনের কন্টেন্ট সংরক্ষণের খরচ। প্রথম রিকোয়েস্টে বা cache মেয়াদ শেষ হওয়ার পরে ঘটে।
- **Cache পড়া**: আগে থেকে সংরক্ষিত কথোপকথন পুনরায় ব্যবহারের খরচ। সাধারণ ইনপুটের তুলনায় **৯০% ছাড়ে** চার্জ হয়।

AI কোডিং টুলগুলো অনিবার্যভাবে দীর্ঘ কথোপকথন এবং বড় কনটেক্সট তৈরি করে, প্রতি রিকোয়েস্টে ১০ লক্ষ টোকেন পর্যন্ত। আপনার নতুন প্রশ্ন ছোট হলেও, পুরো আগের কথোপকথন এর সাথে বিল হয়, তাই কথোপকথন দীর্ঘ হলে খরচ দ্রুত জমা হয়।

এই বোঝা কমাতে, প্রধান AI প্রদানকারীরা cache পড়ায় ৯০% ছাড় দেয়, যা ইতিমধ্যে প্রক্রিয়াকৃত কন্টেন্ট পুনরায় পাঠানোর খরচ উল্লেখযোগ্যভাবে কমায়।

## Cache কেন মোট খরচে প্রাধান্য বিস্তার করে?

| বিভাগ | প্রতি কলে টোকেন | নোট |
|---|---|---|
| ব্যবহারকারীর ইনপুট (নতুন টোকেন) | দশ থেকে শত | ব্যবহারকারী আসলে যা টাইপ করে |
| AI আউটপুট | শত থেকে হাজার | AI-এর উত্তর |
| **Cache পড়া** | **100K থেকে কয়েক লক্ষ** | সম্পূর্ণ জমা কথোপকথন প্রতি কলে বিল হয় |

প্রতি কলে cache পড়ার পরিমাণ ইনপুটের চেয়ে **হাজার গুণ** বেশি। ৯০% ছাড়ের পরেও, ডলারের পরম মূল্যে cache পড়া প্রাধান্য বিস্তার করে।

এবং এই কলগুলো শুধু ব্যবহারকারীর মেসেজ থেকে আসে না:

| কলার | ফ্রিকোয়েন্সি | প্রতি কলে Cache পড়া |
|---|---|---|
| ব্যবহারকারীর মেসেজ | ব্যবহারকারী মেসেজ পাঠালে | সম্পূর্ণ জমা কথোপকথন |
| **AI-এর নিজস্ব সিদ্ধান্ত** | **প্রতি ব্যবহারকারী মেসেজে একাধিক কল** | সম্পূর্ণ জমা কথোপকথন |

অদৃশ্যভাবে, AI একটি ব্যবহারকারী মেসেজের জন্য ক্রমানুসারে একাধিক সিদ্ধান্ত নেয় — কোন টুল ব্যবহার করতে হবে, টুলের ফলাফল ব্যাখ্যা করা, পরবর্তী পদক্ষেপ ঠিক করা। এই প্রতিটি সিদ্ধান্ত একটি সম্পূর্ণ LLM কল যা পুরো কনটেক্সট অন্তর্ভুক্ত করে। টুলের কার্যকর নিজেই (ফাইল পড়া, সার্চ) স্থানীয়ভাবে চলে, কিন্তু প্রতিটি টুল ব্যবহারের আগে ও পরে সিদ্ধান্ত গ্রহণে cache পড়ার খরচ যুক্ত হয়।

### Cache লেখার খরচও কেন প্রত্যাশার চেয়ে বেশি?

Anthropic-এ, cache লেখার খরচ ইনপুটের 1.25 গুণ (5-মিনিট টিয়ার) বা 2 গুণ (1-ঘণ্টা টিয়ার)। এই গুণকগুলোতে মনে হয় cache লেখা ইনপুট+আউটপুট খরচের 2 গুণের বেশি হওয়া উচিত নয় — কিন্তু বাস্তবে cache লেখা অনেক বড় অংশ নেয়।

দুটি কারণ:

| কারণ | ব্যাখ্যা |
|---|---|
| **System prompt** | ব্যবহারকারী কিছু টাইপ করার আগেই দশ হাজার টোকেন (প্লাগইন/MCP সহ)। এর সবকিছু cache লেখার খরচের আওতায় |
| **মেয়াদ শেষের পরে পুনর্নির্মাণ** | TTL (5 মিনিট / 1 ঘণ্টা) শেষ হওয়ার পরে, সম্পূর্ণ জমা কথোপকথন পুনরায় cache করতে হয়। কথোপকথন যত দীর্ঘ, পুনর্নির্মাণ খরচ তত বেশি |

অন্যভাবে বলতে গেলে, cache লেখা শুধু "ব্যবহারকারীর টাইপ করা নতুন টোকেন"-এর জন্য হয় না। সেশনের শুরুতে, সম্পূর্ণ system prompt cache হয়; মেয়াদ শেষের পরে, সম্পূর্ণ জমা কথোপকথন cache লেখার টার্গেট হয়ে যায়। যদি 100K-টোকেনের কথোপকথনের cache মেয়াদ শেষ হয়, একটি মাত্র মেসেজ একবারে 100K-টোকেন cache লেখা ট্রিগার করে।

**এই কারণেই super-token-saver প্লাগইন ১ ঘণ্টা নিষ্ক্রিয়তার পরে cache মেয়াদ শেষের সতর্কতা দেখায়।** সতর্কতা দেখা দিলে, আপনার বর্তমান কনটেক্সটের আকার পরীক্ষা করুন:

- **ছোট কনটেক্সট**: Cache পুনর্নির্মাণ খরচ সামলানো যায়। কাজ চালিয়ে যান — খরচ কম।
- **বড় কনটেক্সট**: Cache খরচ উল্লেখযোগ্য হবে। আমরা `/clear` করার পরে `/s-continue last` চালানোর পরামর্শ দিই নতুন সেশনে কাজ চালিয়ে যেতে। continue স্কিল স্বয়ংক্রিয়ভাবে আপনার আগের কথোপকথনের কনটেক্সট পুনরুদ্ধার করে, তাই আপনার কর্মপ্রবাহ বাধাগ্রস্ত হয় না।

## Cache খরচ কমানোর কৌশল

super-token-saver প্লাগইন এই সমস্ত কৌশল স্বয়ংক্রিয় বা সহজ করতে ডিজাইন করা হয়েছে।

### 1. কনটেক্সট ছোট রাখুন — `/clear` + `/s-continue` ⭐

**খরচ কমানোর এটিই সবচেয়ে গুরুত্বপূর্ণ উপায়।** উচ্চ cache খরচ মানে আপনি ৯০% ছাড় পাচ্ছেন — এটি স্বাভাবিক। কিন্তু কনটেক্সট অপ্রয়োজনীয়ভাবে বড় হলে এবং সেভাবে থাকলে, ছাড়ের পরেও প্রতি কলে পরম খরচ বাড়ে। **কনটেক্সটের আকার নিয়ন্ত্রণে রাখা সবচেয়ে কার্যকর খরচ ব্যবস্থাপনা কৌশল।**

বিষয় পরিবর্তন হলে বা কথোপকথন দীর্ঘ হলে, রিসেট করতে `/clear` চালান, তারপর আগের কনটেক্সট পুনরুদ্ধার করতে `/s-continue last`। `/s-continue` কোনো LLM কল ছাড়াই আগের কথোপকথন পুনরুদ্ধার করে, তাই খরচ শূন্য।

`/compact` কথোপকথন সংক্ষেপ করে কনটেক্সট কমায়, কিন্তু সংক্ষেপ প্রক্রিয়ায় LLM কলের খরচ হয় এবং কথোপকথনের বিস্তারিত হারিয়ে যায়। সুপারিশ করা হয় না।

### 2. Cache মেয়াদ শেষ হওয়া প্রতিরোধ করুন — Token Guardian (স্বয়ংক্রিয়)

Anthropic-এর প্রধান সেশন cache **1-ঘণ্টা টিয়ার** ব্যবহার করে। মেয়াদ শেষের পরে, প্রথম রিকোয়েস্টকে সম্পূর্ণ কথোপকথন cache লেখা হিসেবে পুনর্নির্মাণ করতে হয়, যা ব্যয়বহুল।

super-token-saver ১-ঘণ্টা নিষ্ক্রিয় অবস্থা শনাক্ত করে এবং **স্বয়ংক্রিয়ভাবে সতর্কতা দেখায়**। সতর্কতা দেখা দিলে, উপরের পদ্ধতি 1 (`/clear` + `/s-continue`) ব্যবহার করে নতুন সেশনে চালিয়ে যাওয়া সবচেয়ে সাশ্রয়ী পদ্ধতি।

### 3. ভারী কাজ SubTasks-এ অর্পণ করুন

কোড জেনারেশন বা মাল্টি-ফাইল এডিটের মতো ভারী কাজগুলো মূল সেশনে সরাসরি চালানোর পরিবর্তে SubTasks-এ অর্পণ করা যায়। SubTasks 5-মিনিট cache টিয়ার ব্যবহার করে, যা **cache লেখা 37.5% সস্তা** করে, এবং একটি আলাদা ছোট কনটেক্সটে চলে, যা প্রতি কলে cache পড়ার পরিমাণ কমায়।

super-token-saver সেশন শুরুতে এই কাজ-বিভাজন প্যাটার্নে স্বয়ংক্রিয়ভাবে গাইড করে।

### 4. রিয়েল-টাইম খরচ মনিটরিং — `/setup-statusline`

আপনার CLI-এর নিচে রিয়েল-টাইম খরচ/টোকেন স্ট্যাটাস দেখাতে `/setup-statusline` ইনস্টল করুন: `[RUN] \$0.10/\$12.23 | [5H] 9% | [CTX] 22%`। আপনি অস্বাভাবিকভাবে উচ্চ প্রতি-কল খরচ বা বাড়তে থাকা কনটেক্সট তাৎক্ষণিকভাবে শনাক্ত করতে পারবেন, খরচ বাড়ার আগেই ব্যবস্থা নিতে পারবেন।

### 5. খরচ প্যাটার্ন বিশ্লেষণ — `/usage-view`

আপনার সম্পূর্ণ ব্যবহারের ইতিহাস ড্যাশবোর্ড হিসেবে দেখতে `/usage-view` ব্যবহার করুন। দৈনিক/ঘণ্টা ভিত্তিক খরচের প্রবণতা, প্রতি-সেশন টোকেন গঠন, এবং cache কার্যকারিতা ভিজ্যুয়ালাইজ করুন। এক নজরে দেখুন কোন কাজগুলো খরচ বাড়িয়েছে এবং কোন প্যাটার্নগুলো অদক্ষ।

### 6. System Prompt অপ্টিমাইজেশন

System prompt-এ যত বেশি প্লাগইন, MCP সার্ভার এবং স্কিল লোড হবে, প্রাথমিক cache লেখার খরচ তত বেশি হবে। যা ব্যবহার করছেন না তা সরিয়ে ফেলুন।

super-token-saver-এর `/setup-git-lite` Claude Code-এর ডিফল্ট Git নির্দেশনা (প্রায় 2,200 টোকেন) মূল 280 টোকেনে কমিয়ে দেয় — প্রতি সেশনে Git-সম্পর্কিত system prompt-এ প্রায় 88% হ্রাস।

### 7. টুল নির্বাচন — কনটেক্সটে প্রভাব টুল অনুযায়ী ভিন্ন

একবার কোনো ফাইল পড়া হলে, এর কন্টেন্ট কনটেক্সটে থাকে এবং পরবর্তী সব কলে cache পড়ায় জমা হতে থাকে। একটি ফাইল পুরো পড়লে কনটেক্সটে হাজার থেকে দশ হাজার টোকেন যোগ হয়, এবং সেই পরিমাণ প্রতিটি পরবর্তী কলে বিল হয়।

কোডিং কাজে প্রায়ই একসাথে একাধিক ফাইল জড়িত থাকে — মাত্র 3-4টি ফাইল পুরো পড়লেই কনটেক্সট নাটকীয়ভাবে বাড়তে পারে। সঠিক টুল বেছে নেওয়া কনটেক্সট বৃদ্ধিতে উল্লেখযোগ্য পার্থক্য তৈরি করে।

| টুল | উদ্দেশ্য | কনটেক্সট প্রভাব | কখন ব্যবহার করবেন |
|---|---|---|---|
| **Grep** | প্যাটার্ন দিয়ে কোড সার্চ | **ন্যূনতম** — শুধু মিলে যাওয়া লাইন ফেরত দেয় | নির্দিষ্ট ফাংশন নাম, ভেরিয়েবল, স্ট্রিং খুঁজতে |
| **Glob** | নাম প্যাটার্ন দিয়ে ফাইল সার্চ | **ন্যূনতম** — শুধু ফাইল পাথ ফেরত দেয় | `*.ts`, `src/**/*.test.js` ধরনের ফাইল খুঁজতে |
| **LSP** | সিম্বল ডেফিনিশন, রেফারেন্স, টাইপ | **ন্যূনতম** — শুধু ডেফিনিশন/সিগনেচার ফেরত দেয় | ডেফিনিশনে যেতে, রেফারেন্স খুঁজতে, টাইপ চেক করতে |
| **Read** (offset/limit) | ফাইলের নির্দিষ্ট অংশ পড়া | **মাঝারি** — শুধু নির্দিষ্ট রেঞ্জ ফেরত দেয় | যখন নির্দিষ্ট লাইন রেঞ্জ প্রয়োজন |
| **Read** (পুরো) | সম্পূর্ণ ফাইল পড়া | **বড়** — পুরো ফাইল কনটেক্সটে যোগ হয় | শুধু যখন পুরো ফাইলের গঠন বুঝতে হবে |

"এই পুরো ফাইলটি পড়ো" "এই ফাংশনটি খুঁজে দাও"-এর চেয়ে দশ থেকে শত গুণ বেশি কনটেক্সট ব্যবহার করে।

একই নীতি এডিটিং এবং তুলনায় প্রযোজ্য:

| টুল | উদ্দেশ্য | কনটেক্সট প্রভাব |
|---|---|---|
| **Edit** | বিদ্যমান ফাইল পরিবর্তন | **ন্যূনতম** — শুধু diff কনটেক্সটে যোগ হয় |
| **Write** | নতুন ফাইল তৈরি / সম্পূর্ণ পুনর্লিখন | **বড়** — পুরো ফাইল কনটেক্সটে যোগ হয় |
| **git diff / diff** | ফাইল/ফোল্ডার তুলনা | **ন্যূনতম** — শুধু পার্থক্যগুলো ফেরত আসে |
| দুটি ফাইল আলাদাভাবে পড়া | ফাইল/ফোল্ডার তুলনা | **বড়** — দুটি পুরো ফাইলই কনটেক্সটে যোগ হয় |

super-token-saver সেশন শুরুতে AI-কে এই টুল নির্বাচন গাইড স্বয়ংক্রিয়ভাবে ইনজেক্ট করে, প্রথমে হালকা টুল ব্যবহারে উৎসাহিত করে।

## পরিশিষ্ট: AI প্রদানকারীদের মধ্যে Cache তুলনা

### Cache খরচ

| প্রদানকারী | Cache লেখার খরচ | Cache পড়ার ছাড় | Cache সংরক্ষণ খরচ |
|---|---|---|---|
| **Anthropic**<br/>(Claude Code) | 5-মিনিট টিয়ার: 1.25x ইনপুট<br/>1-ঘণ্টা টিয়ার: 2x ইনপুট | 90% ছাড় | নেই |
| **OpenAI**<br/>(Codex) | কোনো প্রিমিয়াম নেই (ইনপুটের সমান) | 90% ছাড় | নেই |
| **Google Gemini**<br/>(Gemini CLI) | কোনো প্রিমিয়াম নেই (ইনপুটের সমান) | 90% ছাড় | নেই |

> **দ্রষ্টব্য**: Cache পড়ার ছাড়ের হার মডেল অনুযায়ী ভিন্ন। এই তথ্যগুলো প্রতিটি প্রদানকারীর সর্বশেষ ফ্ল্যাগশিপ মডেল প্রতিফলিত করে।

### Cache আয়ুষ্কাল (TTL)

| প্রদানকারী | TTL | গ্যারান্টি |
|---|---|---|
| **Anthropic**<br/>(Claude Code) | 5 মিনিট বা 1 ঘণ্টা | **স্পষ্টভাবে সংজ্ঞায়িত** |
| **OpenAI**<br/>(Codex) | সাধারণত 5-10 মিনিট নিষ্ক্রিয়তার পরে মুছে যায়; অফ-পিক সময়ে 1 ঘণ্টা পর্যন্ত থাকতে পারে | **গ্যারান্টি নেই** — অফিসিয়াল ডক "সাধারণত", "পর্যন্ত" ব্যবহার করে |
| **Google Gemini**<br/>(Gemini CLI) | অপ্রকাশিত | **গ্যারান্টি নেই** — গ্যারান্টিযুক্ত TTL সহ স্পষ্ট caching API-এর মাধ্যমে পাওয়া যায় (অর্থ প্রদান সাপেক্ষে) |

> **দ্রষ্টব্য**: Claude Code নিয়ে আমাদের পরীক্ষার ভিত্তিতে, প্রধান সেশনগুলো সাধারণত 1-ঘণ্টা টিয়ার ব্যবহার করে, আর SubTasks 5-মিনিট টিয়ার ব্যবহার করে।

### সরাসরি API কলের মাধ্যমে অতিরিক্ত Cache নিয়ন্ত্রণ অপশন

উপরের তুলনাটি AI কোডিং টুল ব্যবহারকারীদের (Claude Code, Codex, Gemini CLI) দৃষ্টিকোণ থেকে। সরাসরি API কল করা ডেভেলপারদের কাছে আরো সূক্ষ্ম cache নিয়ন্ত্রণ আছে।

**Anthropic**

- `cache_control`: Cache সীমানা স্পষ্টভাবে নির্ধারণ করতে ব্রেকপয়েন্ট সেট করুন। নির্দিষ্ট না করলে স্বয়ংক্রিয়ভাবে নির্ধারিত হয়।
- TTL টিয়ার (5 মিনিট / 1 ঘণ্টা) প্রতি রিকোয়েস্টে নির্বাচন করা যায়।

**OpenAI**

- `prompt_cache_key`: একই কী-এর রিকোয়েস্টগুলো একই সার্ভারে রুট করে, cache হিট রেট উন্নত করে। Codex অভ্যন্তরীণভাবে এটি `conversation_id`-তে স্বয়ংক্রিয়ভাবে সেট করে।
- `prompt_cache_retention: "24h"`: বর্ধিত cache ধারণ। ডিফল্ট 5-10 মিনিটকে 24 ঘণ্টা পর্যন্ত বাড়ায় (কোনো অতিরিক্ত খরচ নেই, গ্যারান্টি নেই)। Codex এই অপশন ব্যবহার করে না।

**Google Gemini**

- স্পষ্ট caching (`CachedContent`): Cache হিট নিশ্চিত করতে 1 মিনিট থেকে 48 ঘণ্টা পর্যন্ত TTL সেট করুন। সংরক্ষণ ফি প্রযোজ্য (Pro-এর জন্য \$4.50/MTok/ঘণ্টা)। Cache কন্টেন্ট আপডেটের জন্য ম্যানুয়ালি নতুন CachedContent তৈরি করতে হয়। Gemini CLI এই ফিচার ব্যবহার করে না।

> **দ্রষ্টব্য**: এই অপশনগুলো AI কোডিং টুলে উন্মুক্ত নয় এবং ব্যবহারকারীরা সরাসরি নিয়ন্ত্রণ করতে পারে না। AI কোডিং টুল ব্যবহারকারীদের মূল পাঠ্যে "Cache খরচ কমানোর কৌশল" অনুচ্ছেদটি দেখা উচিত।
