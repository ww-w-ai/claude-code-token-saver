# Руководство по кэшу — почему основная часть расходов приходится на кэш

Для большинства инструментов AI-кодинга основная доля затрат приходится на операции с кэшем (запись + чтение). В этом документе объясняется, почему так происходит и как этим управлять.

## Секрет: каждое сообщение заново отправляет весь диалог

Большие языковые модели **не имеют состояния**. В отличие от людей, AI-модели не «помнят» предыдущий разговор — они получают полную историю диалога на каждый запрос.

Выглядит как чат, но на уровне API это работает так:

```
[ Запрос 1 ]
→ Системный промпт + "Исправь этот баг"
← Ответ AI

[ Запрос 2 ]
→ Системный промпт + "Исправь этот баг" + Ответ AI + "Добавь ещё тесты"
← Ответ AI

[ Запрос 3 ]
→ Системный промпт + "Исправь этот баг" + Ответ AI + "Добавь ещё тесты" + Ответ AI + "Закоммить"
← Ответ AI
```

Каждый запрос включает **весь** предыдущий контент. Например, 50-й запрос содержит полный диалог и все ответы AI за предыдущие 49 запросов. Именно поэтому количество входных токенов растёт стремительно по мере удлинения диалога.

Кроме того, инструменты AI-кодинга отправляют системный промпт (встроенные инструкции, конфигурационные файлы, плагины, определения инструментов MCP и т. д.) с каждым запросом — поэтому даже однострочное сообщение превращается в десятки тысяч входных токенов.

## Что такое кэширование?

**Prompt caching** снижает стоимость повторной передачи данных. Неизменённые части запроса сохраняются на сервере, чтобы последующие запросы могли использовать их со скидкой.

- **Cache Write**: стоимость сохранения контента диалога на сервере. Возникает при первом запросе или после истечения кэша.
- **Cache Read**: стоимость повторного использования уже сохранённого контента. Оплачивается со **скидкой 90%** по сравнению со стандартным вводом.

Инструменты AI-кодинга неизбежно порождают длинные диалоги и большие контексты — до 1 миллиона токенов на запрос. Даже если ваш новый вопрос короткий, весь предыдущий диалог оплачивается вместе с ним, поэтому расходы быстро накапливаются по мере роста диалога.

Чтобы снизить эту нагрузку, ведущие AI-провайдеры предоставляют скидку 90% на чтение кэша, что значительно удешевляет повторную передачу уже обработанного контента.

## Почему кэш доминирует в общей стоимости?

| Категория | Токенов за вызов | Примечание |
|---|---|---|
| Пользовательский ввод (новые токены) | Десятки-сотни | То, что пользователь реально вводит |
| Вывод AI | Сотни-тысячи | Ответ AI |
| **Cache read** | **100К–сотни тысяч** | Весь накопленный диалог оплачивается при каждом вызове |

Объём cache read за вызов **в тысячи раз** больше пользовательского ввода. Даже со скидкой 90% cache read доминирует в абсолютных затратах.

И эти вызовы происходят не только от пользовательских сообщений:

| Инициатор | Частота | Cache Read за вызов |
|---|---|---|
| Сообщения пользователя | При отправке сообщения | Весь накопленный диалог |
| **Собственные решения AI** | **Несколько вызовов на одно сообщение** | Весь накопленный диалог |

Незаметно для пользователя AI выполняет несколько решений последовательно для одного сообщения — выбор инструмента, интерпретация результата, решение о следующем действии. Каждое такое решение — полноценный вызов LLM, включающий весь контекст. Само выполнение инструментов (чтение файлов, поиск) происходит локально, но принятие решений до и после каждого использования инструмента несёт затраты на cache read.

### Почему стоимость Cache Write тоже выше ожидаемой?

У Anthropic стоимость cache write составляет 1,25x от стоимости ввода (5-минутный уровень) или 2x (часовой уровень). При таких множителях кажется, что cache write не должен превышать 2x стоимости ввода/вывода — но на практике cache write занимает гораздо большую долю.

Две причины:

| Причина | Объяснение |
|---|---|
| **Системный промпт** | Десятки тысяч токенов ещё до первого сообщения пользователя (с плагинами/MCP). Всё это облагается стоимостью cache write |
| **Пересоздание после истечения** | После истечения TTL (5 мин / 1 час) весь накопленный диалог необходимо закэшировать заново. Чем длиннее диалог, тем выше стоимость пересоздания |

Иными словами, cache write возникает не только для «новых токенов пользователя». При старте сессии весь системный промпт кэшируется; после истечения кэша весь накопленный диалог становится объектом cache write. Если у 100К-токенного диалога истечёт кэш, одно сообщение вызовет cache write на 100К токенов разом.

**Именно поэтому плагин super-token-saver показывает предупреждение об истечении кэша после 1 часа бездействия.** Когда появляется предупреждение, проверьте текущий размер контекста:

- **Маленький контекст**: стоимость пересоздания кэша невелика. Продолжайте работу — затраты будут небольшими.
- **Большой контекст**: стоимость кэша будет значительной. Рекомендуем выполнить `/clear`, затем `/s-continue last`, чтобы продолжить в новой сессии. Навык continue автоматически восстановит контекст предыдущего диалога, поэтому рабочий процесс не прервётся.

## Стратегии снижения затрат на кэш

Плагин super-token-saver разработан для автоматизации или упрощения всех этих стратегий.

### 1. Держите контекст небольшим — `/clear` + `/s-continue` ⭐

**Это самый важный способ снижения затрат.** Высокие расходы на кэш означают, что вы получаете скидку 90% — это нормально. Но если контекст неоправданно разрастается и остаётся таким, абсолютная стоимость за вызов увеличивается даже со скидкой. **Контроль размера контекста — единственная наиболее эффективная стратегия управления затратами.**

При смене темы или длинном диалоге выполните `/clear` для сброса, затем `/s-continue last` для восстановления контекста. `/s-continue` восстанавливает предыдущие диалоги без вызовов LLM, поэтому стоимость равна нулю.

`/compact` уменьшает контекст путём суммаризации, но сам процесс суммаризации требует вызовов LLM и теряет детали диалога. Не рекомендуется.

### 2. Предотвращение истечения кэша — Token Guardian (автоматически)

Основная сессия Anthropic использует **часовой уровень** кэша. После истечения первый запрос должен пересоздать весь диалог в виде cache write, что обходится дорого.

super-token-saver обнаруживает часовое бездействие и **автоматически показывает предупреждение**. При появлении предупреждения наиболее экономичный подход — использовать метод 1 выше (`/clear` + `/s-continue`) для продолжения в новой сессии.

### 3. Делегируйте тяжёлые задачи в SubTasks

Ресурсоёмкие задачи, такие как генерация кода или редактирование нескольких файлов, можно делегировать SubTasks вместо выполнения в основной сессии. SubTasks используют 5-минутный уровень кэша, что делает **cache write на 37,5% дешевле**, и работают в изолированном небольшом контексте, уменьшая объём cache read за вызов.

super-token-saver автоматически направляет к этому паттерну разделения работы при старте сессии.

### 4. Мониторинг затрат в реальном времени — `/setup-statusline`

Установите `/setup-statusline`, чтобы отображать стоимость/токены в реальном времени в нижней части CLI: `[RUN] \$0.10/\$12.23 | [5H] 9% | [CTX] 22%`. Вы сразу заметите аномально высокую стоимость вызова или растущий контекст и сможете принять меры до резкого скачка расходов.

### 5. Анализ паттернов затрат — `/usage-view`

Используйте `/usage-view` для просмотра полной истории использования в виде дашборда. Визуализируйте ежедневные/почасовые тренды затрат, состав токенов по сессиям и эффективность кэша. Сразу видно, какие задачи вызвали скачки затрат и какие паттерны неэффективны.

### 6. Оптимизация системного промпта

Чем больше плагинов, MCP-серверов и навыков загружено в системный промпт, тем выше начальная стоимость cache write. Удалите всё, что не используете.

`/setup-git-lite` из super-token-saver сокращает стандартные Git-инструкции Claude Code (~2 200 токенов) до базовых 280 токенов — снижение примерно на 88% для Git-инструкций в системном промпте на сессию.

### 7. Выбор инструментов — влияние на контекст зависит от инструмента

Прочитанный файл остаётся в контексте и накапливается в cache read при всех последующих вызовах. Чтение одного файла целиком добавляет тысячи-десятки тысяч токенов в контекст, и эта сумма оплачивается при каждом последующем вызове.

Задачи кодирования часто затрагивают несколько файлов одновременно — чтение всего 3-4 файлов целиком может вызвать резкий рост контекста. Правильный выбор инструмента существенно влияет на рост контекста.

| Инструмент | Назначение | Влияние на контекст | Когда использовать |
|---|---|---|---|
| **Grep** | Поиск кода по шаблону | **Минимальное** — возвращает только совпавшие строки | Поиск конкретных имён функций, переменных, строк |
| **Glob** | Поиск файлов по шаблону имени | **Минимальное** — возвращает только пути к файлам | Поиск файлов: `*.ts`, `src/**/*.test.js` |
| **LSP** | Определения символов, ссылки, типы | **Минимальное** — возвращает только определения/сигнатуры | Перейти к определению, найти ссылки, проверить типы |
| **Read** (offset/limit) | Чтение конкретной части файла | **Умеренное** — возвращает только указанный диапазон | Когда нужен конкретный диапазон строк |
| **Read** (полностью) | Чтение всего файла | **Большое** — весь файл добавляется в контекст | Только когда нужно понять полную структуру файла |

«Прочитай весь файл» использует в десятки-сотни раз больше контекста, чем «Найди эту функцию».

Тот же принцип работает для редактирования и сравнения:

| Инструмент | Назначение | Влияние на контекст |
|---|---|---|
| **Edit** | Изменение существующего файла | **Минимальное** — в контекст добавляется только diff |
| **Write** | Создание нового файла / полная перезапись | **Большое** — весь файл добавляется в контекст |
| **git diff / diff** | Сравнение файлов/папок | **Минимальное** — возвращаются только различия |
| Чтение обоих файлов отдельно | Сравнение файлов/папок | **Большое** — оба файла целиком добавляются в контекст |

super-token-saver автоматически внедряет это руководство по выбору инструментов в AI при старте сессии, поощряя использование лёгких инструментов в первую очередь.

## Приложение: сравнение кэша у разных AI-провайдеров

### Стоимость кэша

| Провайдер | Стоимость Cache Write | Скидка на Cache Read | Стоимость хранения кэша |
|---|---|---|---|
| **Anthropic**<br/>(Claude Code) | 5-мин уровень: 1,25x от ввода<br/>Часовой уровень: 2x от ввода | Скидка 90% | Нет |
| **OpenAI**<br/>(Codex) | Без наценки (равна вводу) | Скидка 90% | Нет |
| **Google Gemini**<br/>(Gemini CLI) | Без наценки (равна вводу) | Скидка 90% | Нет |

> **Примечание**: скидки на cache read различаются в зависимости от модели. Указанные цифры отражают последние флагманские модели каждого провайдера.

### Время жизни кэша (TTL)

| Провайдер | TTL | Гарантия |
|---|---|---|
| **Anthropic**<br/>(Claude Code) | 5 минут или 1 час | **Явно определено** |
| **OpenAI**<br/>(Codex) | Обычно вытесняется через 5-10 мин бездействия; может сохраняться до 1 часа в непиковое время | **Не гарантировано** — в документации используются «generally», «up to» |
| **Google Gemini**<br/>(Gemini CLI) | Не раскрывается | **Не гарантировано** — явное кэширование с гарантированным TTL доступно через API (платно) |

> **Примечание**: по нашим экспериментам с Claude Code, основные сессии обычно используют часовой уровень, а SubTasks — 5-минутный.

### Дополнительные опции управления кэшем через прямые вызовы API

Сравнение выше дано с точки зрения пользователей инструментов AI-кодинга (Claude Code, Codex, Gemini CLI). Разработчики, вызывающие API напрямую, имеют более тонкий контроль над кэшем.

**Anthropic**

- `cache_control`: установка контрольных точек для явного определения границ кэша. Определяется автоматически, если не указано.
- Уровень TTL (5 мин / 1 час) можно выбирать для каждого запроса.

**OpenAI**

- `prompt_cache_key`: направляет запросы с одинаковым ключом на один сервер, повышая вероятность попадания в кэш. Codex автоматически устанавливает его в `conversation_id`.
- `prompt_cache_retention: "24h"`: продлённое хранение кэша. Увеличивает стандартные 5-10 мин до 24 часов (без дополнительной платы, не гарантировано). Codex не использует эту опцию.

**Google Gemini**

- Явное кэширование (`CachedContent`): установка TTL от 1 мин до 48 часов для гарантированного попадания в кэш. Взимается плата за хранение (\$4,50/MTok/час для Pro). Обновление содержимого кэша требует создания нового CachedContent вручную. Gemini CLI не использует эту функцию.

> **Примечание**: эти опции недоступны в инструментах AI-кодинга и не могут быть напрямую управляемы пользователями. Пользователям инструментов AI-кодинга следует обратиться к разделу «Стратегии снижения затрат на кэш» в основном тексте.
